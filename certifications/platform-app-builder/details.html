Fondamentaux Salesforce

Où s'arrête le déclaratif

Scénario type : Universal Containers veut qu'un commercial saisisse une demande en trois écrans, qu'un enregistrement soit créé et qu'un service externe de notation soit interrogé. Un Screen Flow, un Create Records et un HTTP Callout suffisent. Aucun besoin d'Apex.

  • Les questions glissent souvent un mot décisif : « without code », « minimal maintenance », « admins must be able to change it ». Il écarte les réponses Apex, même quand elles fonctionnent.
  • À l'inverse, « custom interface that no standard component provides » ouvre la porte à LWC.
Pourquoi c'est testéLe rôle d'App Builder consiste à savoir jusqu'où aller sans développeur, et à reconnaître le moment où il faut en appeler un.

Étendre l'org avec AgentExchange

Scénario type : l'équipe commerciale veut signer électroniquement ses contrats dans deux semaines, sans développeur. La bonne démarche : chercher une solution sur AgentExchange, l'installer en sandbox, vérifier qu'elle convient, puis l'installer en production.

  • Comparer acheter et construire : coût de licence, couverture du besoin, maintenance. Une solution générique et mature l'emporte sur un développement interne.
  • AgentExchange expose aussi des composants à déposer dans Lightning App Builder : ils apparaissent dans la palette, sous la rubrique Custom - Managed après installation.
  • Le catalogue inclut désormais des agents, des actions d'agent et des serveurs MCP : une question peut demander comment doter un agent d'une capacité prête à l'emploi.
  • Le choix du périmètre d'installation (admins, tous, profils choisis) décide des droits accordés sur les composants du package.
PiègeUn composant géré se met à jour par son éditeur : on ne peut pas modifier son code pour l'adapter.

Accès aux objets, enregistrements et champs

Scénario type : tous les commerciaux partagent le profil Sales User. Cinq d'entre eux doivent supprimer des opportunités. On ne clone pas le profil : un Permission Set avec le droit Delete, attribué à ces cinq personnes, suffit.

  • Pour un ensemble de droits récurrent, un Permission Set Group regroupe plusieurs Permission Sets ; un Muting Permission Set y retire un droit pour un cas particulier sans modifier le groupe source.
  • Ordre de lecture d'un problème d'accès : droit sur l'objet, puis accès à l'enregistrement, puis FLS.
  • Exemple de Restriction Rule : des prestataires ne voient que les tâches qu'ils possèdent, même si l'OWD des activités leur en ouvrirait davantage.
  • Exemple de Scoping Rule : un conseiller voit par défaut les clients de son agence, mais peut élargir sa recherche.
  • Une seule Restriction Rule active devrait s'appliquer à un utilisateur donné sur un objet.
PiègeView All sur un objet donne accès en lecture à tous ses enregistrements, sans passer par le partage : c'est souvent la mauvaise réponse quand le besoin n'est que partiel.

Choisir la bonne solution de partage

Scénario type : OWD Private sur Opportunity. L'équipe Finance doit lire toutes les opportunités supérieures à 100 000 $. Une Sharing Rule par critères, vers le groupe public Finance, en lecture seule. Pas besoin de modifier l'OWD ni la hiérarchie.

  1. Définir l'OWD pour l'utilisateur qui doit voir le moins.
  2. Laisser la hiérarchie des rôles ouvrir vers le haut.
  3. Ajouter des Sharing Rules pour les exceptions latérales.
  4. Garder le partage manuel et les équipes pour le cas par cas.
  • Si le partage doit suivre une personne référencée dans un champ lookup, ni la Sharing Rule ni le manuel ne conviennent : c'est un cas d'Apex managed sharing, donc programmatique.
  • Le propriétaire d'un enregistrement et ses supérieurs gardent l'accès, sauf si « Grant Access Using Hierarchies » est décoché sur un objet personnalisé.
  • Pour un objet detail, régler le partage sur le master.
Pourquoi c'est testéLes scénarios combinent un OWD, un groupe d'utilisateurs et une condition ; il faut trouver la plus petite ouverture qui répond au besoin.

Data Modeling and Management · 20 %

Modélisation et gestion des données

Choisir le modèle de données

Scénario type : un même étudiant suit plusieurs cours, et un cours compte plusieurs étudiants ; on veut la note de chaque inscription. Objet de jonction Inscription, avec deux master-detail (Étudiant, Cours) et un champ Note.

  • La note appartient à la relation, pas à l'étudiant ni au cours : c'est le signe qu'un objet de jonction est nécessaire.
  • Pour un objet commun à plusieurs équipes avec des valeurs différentes : Record Types et mises en page, pas un objet par équipe.
  • Un champ qui devient une liste de valeurs répétées (Contact_1, Contact_2…) annonce un objet enfant.
  • Schema Builder aide à concevoir et documenter un modèle visuellement, sans remplacer la mise à jour des mises en page et des droits.
Pourquoi c'est testéLe choix du modèle commande le partage, les roll-ups et les rapports. La mauvaise relation se paie partout ensuite.

Relations : effets sur l'accès, l'interface, les rapports

Scénario type : les lignes de frais n'ont pas de sens sans note de frais, le manager doit voir le total, et l'accès suit celui de la note. Master-detail : suppression en cascade, partage hérité, roll-up sur le total.

  • Une lookup convient quand l'enfant vit seul : un cas peut exister sans produit référencé.
  • Lookup : options à la suppression du parent. Clear the value (défaut), Don't allow deletion, Delete this record also selon la configuration.
  • Le roll-up ne remonte que d'un niveau : pour un grand-parent, roll-up d'un roll-up ou Flow.
  • Un enregistrement de jonction disparaît avec l'un ou l'autre de ses masters ; supprimé avec les deux, il ne se restaure pas.
  • Le partage sur une jonction dépend de l'accès aux deux masters et de l'option Sharing Setting du champ.
  • Lookup Filter : limite les enregistrements proposés dans une lookup, par exemple aux contacts du compte courant.
PiègeUne conversion échoue pour une raison simple : valeur vide côté lookup, ou roll-up existant côté master-detail. Un roll-up supprimé doit aussi disparaître de la corbeille des champs.

Choisir ou changer un type de champ

Scénario type : un champ Text contient des références comme 00421. Le passer en Number supprime les zéros significatifs. Il reste en Text, éventuellement avec External ID et unicité.

  • Risques en cas de type Multi-Select : pas de comparaison simple dans une formule (INCLUDES seulement), regroupements difficiles dans les rapports.
  • Avant de changer un type : vérifier les automatisations, les rapports et les intégrations qui lisent le champ.
  • Option prudente : nouveau champ, migration par Data Loader ou Flow, contrôle, puis retrait de l'ancien.
  • Une picklist restreinte refuse par API les valeurs absentes de la liste.
  • External ID : Text, Number, Email ou Auto Number. Avec l'option Unique, il empêche les doublons sur cette valeur.
PiègeSalesforce affiche un avertissement de perte de données, mais ne propose pas d'annulation : la sauvegarde se fait avant.

Import, export et données externes

Scénario type : importer 200 000 lignes de commandes rattachées à des comptes identifiés par un numéro ERP. Data Loader en upsert, avec un champ External ID sur Account pour résoudre la relation.

  1. Nettoyer les données, supprimer les doublons, contrôler les valeurs de picklists.
  2. Créer les champs manquants, dont les External ID.
  3. Vérifier les règles de validation et automatisations qui peuvent bloquer ou ralentir le chargement.
  4. Charger les parents, puis les enfants.
  5. Contrôler sur un échantillon en sandbox avant la production.
  • Salesforce Connect garde les données à la source : pas de stockage consommé, mais une dépendance à la disponibilité du système externe.
  • External Objects : pas de roll-up, pas de master-detail en tant que detail.
  • Copier des données externes régulièrement : ETL ou API. Accéder à la demande : External Objects.
Pourquoi c'est testéLe seuil de 50 000, les objets non pris en charge par le Wizard et l'usage de l'External ID reviennent régulièrement.
Business Logic and Process Automation · 32 %

Logique métier et automatisation

Champs formule

Scénario type : afficher sur chaque opportunité le niveau du compte client, et un indicateur Retard si la date de clôture est dépassée. Deux formules, l'une inter-objets, l'autre basée sur TODAY().

// Formule Text inter-objets
Account.Tier__c

// Formule Checkbox
AND( CloseDate < TODAY(), NOT(IsClosed) )

// Picklist dans une formule Text
CASE( TEXT(Priority__c), "High", "P1", "Medium", "P2", "P3" )
  • ISBLANK est préférable à ISNULL, notamment pour les champs texte.
  • Le type renvoyé se choisit à la création ; une formule qui additionne deux Currency renvoie Currency.
  • Une formule ne déclenche aucune automatisation quand sa valeur change avec le temps ; pour agir à une date, utiliser un Scheduled Path ou un flow planifié.
PiègeUne formule ne peut pas lire les enregistrements enfants, ni écrire dans un autre champ.

Champs roll-up summary

Scénario type : compter les lignes de commande dont le statut est Livré sur chaque commande. Roll-up COUNT sur le master, avec filtre Statut = Livré.

  • Filtre : pas de champs Long Text, Multi-Select, Auto Number, ni de formule inter-objets.
  • Les champs agrégeables : Number, Currency, Percent ; Date pour MIN et MAX.
  • La création ou la modification d'un roll-up peut lancer un recalcul sur tous les enregistrements. Prévoir un moment calme.
  • Le recalcul fait repasser le parent par la sauvegarde.
  • Sur lookup, Flow record-triggered couvre création, modification, suppression, et le changement de parent.
PiègeSur une lookup, penser aussi au cas de suppression de l'enfant et au changement de parent, sinon le total se décale.

Règles de validation

Scénario type : interdire qu'une opportunité passe en Closed Won sans date de livraison, sauf pour les responsables disposant d'une permission spécifique.

AND(
  ISCHANGED(StageName),
  ISPICKVAL(StageName, "Closed Won"),
  ISBLANK(Delivery_Date__c),
  NOT($Permission.Bypass_Delivery_Check)
)
  • Un test de longueur sur un champ texte : LEN(Code__c) <> 8.
  • Format contrôlé : NOT(REGEX(Code__c, "[A-Z]{3}-[0-9]{4}")).
  • La conversion de leads ne les applique que si le réglage correspondant est actif.
  • Pour bloquer une suppression, utiliser un flow avant suppression avec Custom Error.
PiègeInverser la logique est l'erreur la plus fréquente : la formule décrit la situation invalide.

Créer et configurer un flow

Scénario type : à la création d'un cas Priorité Haute, avertir le responsable de compte, créer une tâche et positionner un champ Niveau sur le cas. Record-triggered en Actions and Related Records, ou deux flows si l'on veut profiter de Fast Field Updates pour le champ.

  1. Choisir le type et définir l'objet, l'événement et les conditions d'entrée.
  2. Choisir l'optimisation : Fast Field Updates ou Actions and Related Records.
  3. Récupérer les données avec Get Records, en filtrant au plus juste.
  4. Traiter avec Decision, Assignment, Loop, Transform.
  5. Écrire en une seule opération sur une collection.
  6. Ajouter des fault paths sur les éléments qui peuvent échouer.
  7. Tester avec Debug, puis activer.
  • Pour éviter une exécution répétée à chaque mise à jour : conditions d'entrée et « Only when a record is updated to meet the condition requirements ».
  • Un flow qui met à jour le record déclencheur en after-save le fait passer à nouveau par la sauvegarde ; Fast Field Updates l'évite.
  • Screen Flow : composants réactifs à l'écran, validation d'entrée, navigation.
  • Subflow : factorise une logique dans un autolaunched flow, avec variables d'entrée et de sortie.
  • Plusieurs flows sur le même objet : Trigger Order réglé de 1 à 2000 et visualisé dans Flow Trigger Explorer.
PiègeScheduled Paths demande que le flow s'exécute à la création, ou seulement quand la mise à jour fait entrer l'enregistrement dans les conditions.

Processus d'approbation Flow

Scénario type : une remise supérieure à 15 % requiert l'accord du manager, puis celui de la direction financière au-delà de 30 %. Record-triggered Approval Orchestration à deux stages, Decision entre les deux, verrouillage pendant l'approbation.

  1. Créer le flow Record-Triggered Approval Orchestration et ses conditions d'entrée.
  2. Ajouter un stage avec un Approval Step et l'approbateur (User, Queue ou Group).
  3. Router selon le résultat avec un Decision.
  4. Ajouter un Background Step pour mettre à jour le statut final.
  5. Prévoir un Recall path et un fault path.
  6. Déboguer, activer, suivre dans l'app Approvals.
  • Un stage se termine par défaut quand toutes ses étapes sont terminées ; une condition personnalisée ou un Evaluation Flow peut changer ce comportement.
  • Les approbateurs répondent par e-mail avec des mots-clés, dans l'Orchestration Work Guide, ou depuis l'app Approvals.
  • Les données sont dans Approval Submission et Approval Work Item, utilisables dans des Custom Report Types.
  • La permission Approval Designer permet de gérer les flows d'approbation autolaunched, avec un passage par « Submit for Activation ».
PiègeTous les approbateurs doivent être déterminés dans l'étape : la sélection manuelle du suivant n'est pas prévue.

Choisir le type de flow

Scénario type : « trente jours avant la fin du contrat, créer une tâche de renouvellement, sauf si le contrat a été annulé ». Record-triggered avec Scheduled Path relatif à la date de fin : l'action n'a pas lieu si l'enregistrement ne remplit plus les conditions.

Formule de l'énoncéType
« user enters », « guide users », « wizard »Screen
« when a record is created or updated »Record-Triggered
« every night », « each Monday »Schedule-Triggered
« called from another flow », « reusable »Autolaunched
« when the external system publishes an event »Platform Event-Triggered
« several teams, in stages »Orchestration
« approve », « approval chain »Approval Orchestration
  • Screen Flow sur une page : composant Flow. Sur un bouton : action rapide ou URL.
  • Schedule-Triggered traite des enregistrements par lots, $Record représentant chacun d'eux.
  • Une action d'agent repose sur un autolaunched flow.
Pourquoi c'est testéC'est l'objectif ajouté en 2026 qui demande le plus de discernement. Les réponses incorrectes sont généralement des flows réels, simplement inadaptés.

Maintenir, surveiller, dépanner

Scénario type : un flow record-triggered échoue en production avec un message générique. L'admin lit l'e-mail d'erreur, ouvre l'interview en échec dans Paused and Failed Flow Interviews, identifie l'élément, reproduit avec Debug sur l'enregistrement concerné, puis enregistre une nouvelle version.

SymptômeOù regarder

  • Écran d'erreur utile à l'utilisateur : fault path vers un écran, avec un message clair et $Flow.FaultMessage consigné.
  • Une interview en pause conserve sa version de flow.
  • Une version ne se supprime pas tant que des interviews lui sont rattachées.
  • Roll Back Records annule ce qui a été fait dans la transaction courante.
  • Flow Tests : tests réutilisables pour certains flows record-triggered, directement dans Flow Builder.
PiègeUn Get Records sans résultat ne passe pas par le fault path : c'est un succès, à tester avec un Decision avant d'utiliser la variable.

Agentforce pour automatiser

Scénario type : les clients écrivent de façon libre pour modifier leur réservation. Un agent comprend la demande, identifie la réservation et appelle une action qui repose sur un autolaunched flow. Le flow applique les règles strictes.

CritèreFlowAgentforce
EntréeÉvénement ou clicLangage naturel
CheminToujours le mêmeChoisi par raisonnement
RésultatDéterministeVariable, encadré par les instructions

  • Le Subagent délimite un domaine : ce n'est pas une garantie d'autorisation. Le contrôle d'accès reste dans les droits et les actions.
  • Un flow en contexte système ne devient pas sécurisé parce qu'un agent l'appelle.

Options de personnalisation

Scénario type : sur Case, un bloc Remboursement ne doit apparaître que si Type = Remboursement, et seulement pour le service client. Dynamic Forms avec section visible selon le champ et une permission, sans multiplier les mises en page.

  • Priorité d'activation : la combinaison application, type d'enregistrement et profil est la plus spécifique ; l'org default est le filet de sécurité.
  • Dynamic Related List : filtrer et trier une related list directement sur la page.
  • Path : guide les utilisateurs d'étape en étape, avec champs clés et conseils pour chaque valeur.
  • Console : onglets et sous-onglets, pour le travail répétitif et multi-enregistrements.
Pourquoi c'est testéPlusieurs options affichent le même résultat ; il faut choisir la plus simple à maintenir.

Boutons, liens et actions

Scénario type : depuis un compte, créer une opportunité déjà reliée, avec l'étape Prospection préremplie, en mobile comme sur desktop. Action spécifique à l'objet, Create a Record, avec une Predefined Field Value.

  • Lien vers un système externe avec le numéro de commande : bouton ou lien URL avec champ de fusion.
  • Action sur plusieurs lignes sélectionnées : List Button, ou Screen Flow lancé depuis la vue de liste.
  • Screen Flow en action : flow object-specific, qui reçoit recordId.
  • Default field values et mise en page d'action se règlent sur l'action.
PiègeLes boutons URL fonctionnent en Lightning ; le JavaScript exécuté au clic, non.

Ajouter des composants Lightning sans code

Scénario type : ajouter à la page de compte un graphique du chiffre d'affaires, visible uniquement sur desktop. Composant standard Report Chart, filtre de visibilité sur le facteur de forme.

  • Un composant AgentExchange s'ajoute comme un composant standard après installation du package.
  • Pour réutiliser une logique de saisie : screen flow exposé dans le composant Flow.
  • Un composant peut prendre l'Id du record courant sans configuration quand il est conçu pour.
  • Trop de composants ralentissent la page : préférer Tabs ou Accordion, qui chargent à la demande.
PiègePour un même besoin, composant standard d'abord, AgentExchange ensuite, code en dernier.

Composants Lightning personnalisés (programmatique)

Scénario type : un développeur livre un LWC, mais il n'apparaît pas dans Lightning App Builder. Il manque isExposed à true ou la cible de page.

<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
  <apiVersion>67.0</apiVersion>
  <isExposed>true</isExposed>
  <targets>
    <target>lightning__RecordPage</target>
    <target>lightning__AppPage</target>
  </targets>
</LightningComponentBundle>
  • lightning__FlowScreen rend le composant disponible dans un écran de Flow ; lightning__RecordAction, en action.
  • <targetConfigs> permet à l'admin de régler des propriétés sans code.
  • Côté Aura, force:hasRecordId donne accès à l'Id du record courant.
Pourquoi c'est testéUn App Builder ne code pas, mais doit savoir ce qu'il faut pour qu'un composant soit disponible dans ses outils.

Actions et mises en page pour le mobile

Scénario type : les techniciens veulent enregistrer une intervention depuis un compte sur leur téléphone, en trois champs. Action spécifique à l'objet, Create a Record, avec une mise en page réduite et des valeurs prédéfinies.

  • Pour une action disponible partout, sans lien avec un enregistrement : action globale, ajoutée à la Publisher Layout.
  • Pour personnaliser l'action bar d'un objet : section Salesforce Mobile and Lightning Experience Actions ou Dynamic Actions.
  • Les quatre champs du haut de la Compact Layout sont ceux qui s'affichent sur le téléphone : y mettre ce qui sert sur le terrain.
  • Une page d'application peut être rendue disponible sur mobile et ajoutée au menu.
PiègeCompact Layout et Page Layout sont deux réglages distincts : le premier gère le résumé, le second le détail.

Cycle de vie et sandboxes

Scénario type : une petite équipe construit dans un sandbox, puis les métiers valident sur des données ressemblant à la production avant mise en ligne. Developer pour construire, Partial Copy pour l'UAT.

BesoinSandbox
Développer, sans donnéesDeveloper
Charger un grand jeu de données de testDeveloper Pro
Former ou valider sur un échantillon réelPartial Copy
Reproduire un problème de volume ou mesurer les performancesFull
  • Partial Copy impose un sandbox template ; Full le permet en option.
  • Les utilisateurs sont copiés avec des adresses e-mail neutralisées.
  • Un sandbox de Preview reçoit la prochaine version plus tôt : utile pour tester avant une release.
  • Lifecycle Center ajoute Git, des work items et des pipelines, sans ligne de commande.
Pourquoi c'est testéLa question porte presque toujours sur la combinaison données, fréquence de refresh et stockage.

Change sets

Scénario type : un Inbound Change Set échoue car un champ référencé par un flow n'y figure pas. Cloner l'Outbound, ajouter le champ avec View/Add Dependencies, renvoyer, puis valider.

  1. Autoriser la connexion dans l'org cible (Allow Inbound Changes).
  2. Créer l'Outbound, ajouter les composants et dépendances.
  3. Uploader vers l'org cible.
  4. Valider l'Inbound, puis déployer.
  5. Effectuer les étapes manuelles et activer les flows.
  • Les droits d'un nouveau champ passent par un profil inclus ; un Permission Set inclus est plus lisible.
  • Un Inbound ne se réexpédie pas : pour aller à l'org suivante, recréer un Outbound depuis l'org intermédiaire.
  • L'exigence de couverture de test des flows ne concerne pas les flows avec écrans.
PiègeLa suppression d'un champ ne se déploie pas par change set : la faire à la main ou utiliser un outil Metadata API.

Packages gérés et non gérés

Scénario type : un partenaire veut distribuer une application à plusieurs clients et corriger les bugs sans intervention de leur part. Package géré.

  • Un non-géré sert à offrir un point de départ : l'utilisateur en devient responsable.
  • Un géré impose un namespace, créé à partir d'une org dédiée.
  • Dépendances : installer dans l'ordre requis.
  • Tester dans un sandbox avant de l'installer en production.
Pourquoi c'est testéLa question compare le droit de modifier le contenu et la capacité à recevoir des mises à jour.

Plan de déploiement

Scénario type : une mise en production comporte un nouvel objet, deux flows et une page. Le plan : valider en amont, déployer en heures creuses, exécuter les étapes manuelles consignées, activer les flows, vérifier, communiquer.

  • Séparer les changements à risque et prévoir une marche arrière : version précédente du flow à réactiver, sauvegarde de métadonnées.
  • Former les utilisateurs et publier une note de version avant l'ouverture.
  • Si un correctif urgent est nécessaire, partir de la production via un sandbox rafraîchi plutôt que de modifier directement la production.
  • Un environnement de staging proche de la production évite les surprises.
PiègeLe plan doit inclure ce qui n'est pas déployable : réglages, activations, données de référence.
