Salesforce Fundamentals · 18 %

Fondamentaux Salesforce

Frontière entre déclaratif et code, AgentExchange, accès aux objets, enregistrements et champs, partage, rapports et tableaux de bord.

0/5
Objectifs officiels de la section
  • Selon un scénario, identifier où s'arrête la personnalisation déclarative et où le programmatique devient nécessaire.
  • Identifier les cas courants d'extension d'une org via AgentExchange.
  • Appliquer les fonctionnalités qui restreignent ou étendent l'accès aux objets, enregistrements et champs.
  • Selon les besoins métier, choisir la solution de partage adaptée.
  • Identifier les fonctionnalités de création de rapports, types de rapports et tableaux de bord.

Où s'arrête le déclaratif

  • Règle de l'examen : clics avant code. Apex ou LWC ne sont la bonne réponse que si une contrainte l'impose ; une solution « sans code » qui couvre le besoin l'emporte.
  • Couvert en déclaratif : objets, champs, relations, formules, roll-ups, règles de validation, Flow, approbations, Lightning App Builder, Dynamic Forms, actions rapides, rapports. Flow sait aussi appeler une API REST avec HTTP Callout ou External Services.
  • Programmatique nécessaire : interface sur mesure qu'aucun composant standard ni écran de Flow ne couvre (LWC) ; traitement lourd ou très gros volume au-delà des limites de Flow (Apex, Batch) ; web service exposé sur mesure.
  • Fausses frontières : roll-up sur une lookup → Flow record-triggered, sans code ; ancien bouton OnClick JavaScript → action rapide, Flow ou LWC ; champ calculé sur le parent → formule inter-objets.
Piège« Sans code » n'interdit pas une solution packagée d'AgentExchange. « Sans installer de package » l'interdit. Lire la contrainte mot à mot.

Étendre l'org avec AgentExchange

  • Depuis avril 2026, AgentExchange réunit AppExchange, le Slack Marketplace et l'écosystème Agentforce. Le guide d'examen emploie ce nom ; une question plus ancienne peut encore dire AppExchange.
  • On y trouve des applications, des composants Lightning, des agents et actions d'agent, des templates de Flow et des serveurs MCP.
  • Cas types : besoin générique (signature électronique, génération de documents, cartographie), délai court, composant prêt à déposer dans une page Lightning, pas de compétence de développement dans l'équipe.
  • Avant d'installer : tester en sandbox, vérifier l'édition, les licences, les avis et la security review. L'installation se fait pour les admins seulement, pour tous les utilisateurs ou pour des profils choisis.
PiègeInstaller directement en production sans essai en sandbox est la mauvaise réponse classique.

Accès aux objets, enregistrements et champs

NiveauCe qui ouvreCe qui restreint
ObjetProfil, Permission Set, Permission Set GroupProfil minimal, Muting Permission Set (dans un groupe)
ChampFLS via profil ou Permission SetFLS masqué ou en lecture seule
EnregistrementHiérarchie des rôles, Sharing Rules, équipes, partage manuel, territoiresOWD, Restriction Rules
  • Les accès se combinent : pour modifier un enregistrement, il faut le droit Edit sur l'objet, un accès Edit à l'enregistrement et un champ modifiable en FLS.
  • Bonne pratique : profil minimal + Permission Sets. Un Muting Permission Set retire un droit, uniquement à l'intérieur d'un Permission Set Group.
  • View All et Modify All sur un objet passent outre le partage pour cet objet ; View All Data et Modify All Data le font pour toute l'org.
  • La FLS est de la sécurité : elle s'applique dans l'interface, l'API, les rapports et la recherche. Masquer un champ d'une mise en page n'est que de l'affichage.
  • Restriction Rules : ne laissent voir qu'un sous-ensemble d'enregistrements, même si le partage donne plus. Objets : personnalisés, externes, Contract, Event, Quote, Task, TimeSheet, TimeSheetEntry.
  • Scoping Rules : orientent la vue par défaut sans retirer l'accès. Ce n'est pas un contrôle de sécurité.
Piège« Requis » ou « lecture seule » sur une mise en page ne vaut que dans cette interface. Pour l'API et les imports : champ requis universellement, règle de validation ou FLS.

Choisir la bonne solution de partage

BesoinSolution
Niveau de base le plus restrictifOWD (Private, Public Read Only, Public Read/Write, Controlled by Parent)
Les managers voient les données de leur équipeHiérarchie des rôles (Grant Access Using Hierarchies, décochable sur les objets personnalisés)
Partager selon le propriétaireSharing Rule par propriétaire, vers un rôle, un groupe ou un territoire
Partager selon une valeur de champSharing Rule par critères
Cas ponctuel sur un enregistrementPartage manuel, perdu si le propriétaire change
Groupe de travail sur un compte, une opportunité ou un casAccount, Opportunity ou Case Team
Répartition par géographie ou portefeuilleEnterprise Territory Management
File de travail sans propriétaire individuelQueue comme propriétaire
Règle impossible à exprimer autrementApex managed sharing (programmatique)
  • L'OWD est le plancher : tout le partage ne fait qu'ouvrir au-delà. Un mécanisme de partage ne retire jamais un accès.
  • Un Public Group regroupe des utilisateurs, rôles et autres groupes pour simplifier les Sharing Rules.
  • Côté detail d'un master-detail, pas de Sharing Rule, de partage manuel ni de queue : ils exigent un champ Owner.
PiègePour cacher des enregistrements déjà ouverts par le partage, une Sharing Rule ne sert à rien : il faut revoir l'OWD ou ajouter une Restriction Rule.

Rapports, types de rapports, tableaux de bord

  • Formats : Tabular (liste), Summary (groupes en lignes), Matrix (lignes et colonnes), Joined (plusieurs blocs, types de rapports différents).
  • Custom Report Type : jusqu'à 4 objets liés (A → B → C → D), « with » ou « with or without » les enregistrements enfants, statut In Development ou Deployed, jusqu'à 1 000 champs.
  • Enrichir sans créer de champ : bucket, row-level formula, summary formula (5 par rapport), cross filter (par exemple comptes sans opportunité).
  • Tendances : Historical Trending et Reporting Snapshots (un rapport alimente un objet personnalisé à intervalle régulier).
  • Tableaux de bord Lightning : jusqu'à 25 widgets, dont 20 graphiques ou tableaux. Chaque composant repose sur un rapport enregistré.
  • Running user : utilisateur désigné (tous voient ses données) ou utilisateur connecté, soit un dashboard dynamique (5 en Enterprise, 10 en Performance et Unlimited).
PiègeUn champ ajouté à un objet n'apparaît dans un Custom Report Type existant que s'il est ajouté à sa mise en page ou si le réglage d'ajout automatique est actif. Et le lecteur doit avoir la FLS.

Modélisation et gestion des données

Choix du modèle, effets de chaque relation sur l'accès, l'interface et les rapports, changement de type de champ, imports, exports et données externes.

0/4
Objectifs officiels de la section
  • Selon un scénario, déterminer le modèle de données approprié.
  • Expliquer les capacités de chaque type de relation et leur effet sur l'accès aux enregistrements, l'interface et les rapports.
  • Déterminer ce qu'il faut prendre en compte pour choisir ou changer le type de données d'un champ.
  • Déterminer les options et considérations d'import et d'export de données, y compris les sources externes.

Choisir le modèle de données

  • Commencer par l'objet standard si le concept existe (Account, Case…) : il apporte les fonctions natives. Objet personnalisé pour un concept propre au métier.
  • Cardinalité : un-à-plusieurs → lookup ou master-detail ; plusieurs-à-plusieurs → objet de jonction avec deux master-detail ; hiérarchie sur le même objet → self-lookup ; hiérarchie sur User → relation Hierarchical.
  • Record Types quand un objet garde les mêmes champs mais varie par processus, picklists ou mise en page. Objets séparés quand la sécurité ou les champs diffèrent vraiment.
  • Schema Builder : visualise le modèle et crée objets, champs et relations par glisser-déposer. Les nouveaux champs n'arrivent pas sur les mises en page et leur FLS reste à vérifier.
  • Modèles à éviter : un champ par mois ou par année (préférer un objet enfant) et le multi-select pour ce qui doit être filtré ou agrégé.
  • Données qui doivent rester à l'extérieur → External Objects via Salesforce Connect.
PiègeUn enfant qui doit avoir son propre propriétaire ou un partage indépendant ne peut pas être côté detail : il faut une lookup.

  • Limites : 2 master-detail et 40 relations au total par objet. Un objet standard ne peut pas être côté detail. Master-detail sur 3 niveaux au maximum.
  • Lookup → master-detail : seulement si tous les enregistrements ont une valeur. Master-detail → lookup : seulement s'il n'existe aucun roll-up sur le master.
  • Objet déjà rempli : un master-detail ne se crée pas directement. Créer une lookup, la renseigner partout, puis convertir.
  • Jonction : le premier master-detail créé est le primaire ; il donne la couleur et l'icône, l'Owner hérité et la division.
  • External Lookup : le parent est un objet externe. Indirect Lookup : un objet externe enfant, relié à un parent Salesforce par un champ External ID unique.
PiègeUne lookup peut être rendue requise, mais cela ne donne ni partage hérité ni roll-up natif.

Choisir ou changer un type de champ

  • Choisir d'abord selon l'usage : Text pour un code à zéros en tête, Picklist pour des valeurs contrôlées, Global Value Set pour partager une liste, Number ou Currency pour calculer, External ID pour faire correspondre des imports.
  • Picklist dépendante : le champ de contrôle est une picklist ou une case à cocher ; le champ dépendant est une picklist ou un multi-select personnalisé.
  • Impossible à changer : type d'un champ standard, champ Formula, champ chiffré, champ mappé pour la conversion des leads, champ référencé par Apex ou Visualforce, passage entre relation et non-relation.
  • Perte de données : vers Auto Number (sauf depuis Text), vers Multi-Select (sauf depuis Picklist), depuis Multi-Select ou Checkbox, depuis Auto Number (sauf vers Text), Date ↔ Date/Time, Text vers Number/Percent/Currency si le contenu n'est pas numérique, Long Text vers un type plus court (troncature).
  • Picklist → Checkbox : Salesforce demande quelles valeurs correspondent à coché et décoché.
  • Effets de bord : vues de liste, rapports, filtres, automatisations et historique du champ. Exporter les données d'abord, ou créer un nouveau champ et migrer.
PiègeText → Picklist : auditer les valeurs avant et après le changement, car la liste définie ne couvre pas forcément tout ce qui existe dans les enregistrements.

Logique métier et automatisation

Formules, roll-ups, règles de validation, Flow en profondeur, approbations Flow et Agentforce comme outil d'automatisation.

0/8
Objectifs officiels de la section
  • Utiliser des champs formule pour répondre aux besoins métier.
  • Déterminer les capacités, cas d'usage et implications des champs roll-up summary.
  • Utiliser des règles de validation pour répondre aux besoins métier.
  • Créer et configurer des flows dans Flow Builder.
  • Décrire les capacités et cas d'usage des processus d'approbation Flow.
  • Selon un scénario, choisir le type de flow approprié.
  • Maintenir, surveiller et dépanner les flows.
  • Décrire les capacités et cas d'usage d'Agentforce pour automatiser les processus métier.

Champs formule

  • Lecture seule, calculés à l'affichage, non stockés. Types renvoyés : Checkbox, Currency, Date, Date/Time, Number, Percent, Text, Time.
  • Inter-objets : uniquement vers le haut (enfant vers parent), jusqu'à 10 relations. Pour agréger des enfants : roll-up ou Flow.
  • Limites : 3 900 caractères, 5 000 octets compilés (les formules référencées comptent). Découper une formule en plusieurs champs ne réduit pas la taille compilée.
  • Fonctions à reconnaître : ISPICKVAL, TEXT (picklist), INCLUDES (multi-select), ISBLANK, BLANKVALUE, CASE, IF, HYPERLINK, IMAGE, TODAY, ADDMONTHS.
  • ISNEW, ISCHANGED, PRIORVALUE ne servent pas dans un champ formule : ils vont dans une règle de validation ou un flow.
PiègeLe passage du temps recalcule une formule à l'affichage, mais ne déclenche aucun flow ni aucune règle.

Champs roll-up summary

  • Sur le master d'un master-detail : COUNT, SUM, MIN, MAX, avec filtre optionnel. Existe aussi sur quelques relations standard, comme Opportunity → Opportunity Product ou Account → Opportunity.
  • Un roll-up ne peut pas agréger une formule qui contient une référence inter-objets ou une fonction dynamique comme NOW ou TODAY.
  • Limite : 25 par objet, 40 sur demande au support.
  • Pas de master-detail possible : Flow record-triggered (création, mise à jour et suppression des enfants) pour rester déclaratif.
  • Une règle de validation sur le master peut bloquer l'enregistrement d'un enfant si le nouveau total la viole.
PiègeUn master-detail ne peut pas repasser en lookup tant qu'un roll-up existe sur le master.

Règles de validation

  • Formule vraie = erreur, enregistrement bloqué. Message en haut de page ou sur un champ modifiable.
  • S'appliquent à l'interface, à l'API et aux imports. Ne s'exécutent pas à la suppression.
  • Outils : ISCHANGED, PRIORVALUE, ISNEW, ISPICKVAL, REGEX, VLOOKUP (propre aux règles de validation), $User, $Profile, $Permission.
  • Contournement propre : NOT($Permission.Bypass_VR) && …, avec une Custom Permission attribuée par Permission Set, plutôt qu'un test sur le nom de profil.
  • Elles s'exécutent après les flows before-save et les triggers before ; voir l'ordre d'exécution.
PiègeUn champ roll-up ou formule n'est pas sur le formulaire : il peut être testé, mais ne peut pas porter l'emplacement de l'erreur.

Créer et configurer un flow

  • Éléments : Screen, Action, Subflow ; Decision, Assignment, Loop, Collection Sort, Collection Filter, Transform ; Get, Create, Update, Delete Records ; Custom Error, Roll Back Records.
  • Ressources : variables et collections, constantes, formules, choix. $Record donne l'enregistrement déclencheur, $Record__Prior ses valeurs d'avant la mise à jour.
  • Record-triggered : création, mise à jour, création ou mise à jour, suppression. Conditions d'entrée. « Every time » ou « Only when a record is updated to meet the condition requirements ».
  • Fast Field Updates (before-save) : met à jour le seul enregistrement déclencheur par Assignment, sans DML supplémentaire. Actions and Related Records (after-save) : tout le reste.
  • Scheduled Paths : décalés par rapport à une date ou au déclenchement, after-save seulement. Run Asynchronously : callout ou traitement après le commit.
  • Bulkification : jamais de Get, Create, Update ou Delete dans un Loop. Assembler une collection, puis un seul Update Records.
  • Contexte : les flows déclenchés s'exécutent en contexte système ; un screen flow, en contexte utilisateur par défaut.
PiègeUne action ou la mise à jour d'un autre objet oblige à choisir Actions and Related Records : Fast Field Updates ne le permet pas.

Processus d'approbation Flow

  • Deux types de flow : Record-Triggered Approval Orchestration et Autolaunched Approval Orchestration (lancé par un bouton ou un autre processus). Disponibles depuis Spring '25, sans coût additionnel.
  • Structure : stages en séquence, composés de steps. Approval Step interactif (screen flow, approbateurs, notification, verrouillage du record) ; Background Step via autolaunched flow.
  • Approbateurs : User, Queue ou Group. Decision pour router selon le résultat. Depuis Summer '26, approbation à l'unanimité plus simple.
  • Suivi : app Approvals (Approval Submissions, Submission Details, Approval Work Items), composant Approval Trace sur le record. Recall path et fault paths depuis Summer '25, Debug depuis Winter '26.
  • Par rapport au processus classique : logique dans Flow Builder, branchements et étapes parallèles. La related list Approval History reste vide.
PiègeLes Classic Approval Processes existent encore, mais les objectifs d'examen parlent désormais d'approbations Flow.

Maintenir, surveiller, dépanner

  • Une version active ne se modifie pas : Save As New Version, tester, puis activer. Une seule version active par flow.
  • Debug dans Flow Builder : valeurs d'entrée, enregistrement déclencheur, mode rollback, exécution en tant qu'un autre utilisateur (à autoriser dans Process Automation Settings).
  • Fault path : chemin alternatif sur un élément de données ou une action. $Flow.FaultMessage donne l'erreur. Une requête Get sans résultat n'est pas une erreur : la tester avec Decision.
  • Sans fault path : message générique, e-mail d'erreur au dernier admin qui a modifié le flow ou aux destinataires Apex (réglage de Process Automation Settings), interview listée dans Paused and Failed Flow Interviews.
  • Surveillance : app Automation, Flow Trigger Explorer pour voir et ordonner les flows d'un objet, Time-Based Workflow pour les chemins planifiés, debug logs pour le détail.
  • Limites à respecter : 100 requêtes SOQL et 150 DML par transaction, partagées avec les autres automatisations.
PiègeUn flow avec fault path n'apparaît pas dans les failed interviews : prévoir sa propre journalisation.

Agentforce pour automatiser

  • Un agent se compose de subagents (ex-topics, renommés en 2026), d'instructions en langage naturel et d'actions. L'examen peut employer l'un ou l'autre terme.
  • Actions possibles : autolaunched flow, prompt template, méthode Apex invocable, API. Un flow existant peut ainsi devenir une action d'agent.
  • Flow : déclencheur fixe, même chemin à chaque fois, enregistrement strict. Agentforce : entrée conversationnelle, demande non structurée, ambiguïté, raisonnement sur plusieurs étapes.
  • Les deux se combinent : l'agent raisonne, le flow exécute de façon déterministe. Une règle stricte (plafond de remboursement) se place dans Flow ou Apex, pas dans une consigne.
  • Sécurité : vérifier l'utilisateur de l'agent, ses droits et les données transmises à chaque action. Tester les demandes hors périmètre et l'escalade vers un humain.
  • Construction dans Agentforce Builder. Einstein Trust Layer intégré.
PiègePas besoin d'être expert d'Agentforce ici : l'examen demande de reconnaître quand c'est le bon outil. Le reste relève de la certification Agentforce Specialist.

Options de personnalisation

  • Lightning App Builder : pages Record, App et Home. Activation par défaut de l'org, par application, ou par combinaison application, type d'enregistrement et profil.
  • Dynamic Forms : champs et sections placés sur la page, avec filtres de visibilité. Objets personnalisés et objets standard compatibles LWC, y compris sur mobile.
  • Dynamic Actions : actions du panneau de surbrillance affichées selon des critères. Filtres de visibilité : champ, permission, appareil.
  • Page Layout : champs, related lists, boutons. Compact Layout : champs clés du panneau de surbrillance et de l'aperçu de lookup.
  • Record Types : picklists, processus et mises en page différents par profil. Path : étapes d'une picklist avec Key Fields et Guidance for Success.
  • Lightning Apps : navigation standard ou console, utility bar, visibilité par profil.
PiègeUn filtre de visibilité masque un composant, pas la donnée : ce n'est pas de la sécurité.

Ajouter des composants Lightning sans code

  • Sources de la palette : composants standard, composants personnalisés exposés, composants AgentExchange installés.
  • Standard utiles : Related List (Single, Dynamic), Rich Text, Report Chart, Tabs, Accordion, Flow, Path, Visualforce, Highlights Panel.
  • Un screen flow se place avec le composant Flow ; il peut recevoir l'Id du record via une variable d'entrée recordId.
  • Les attributs du composant se règlent dans le panneau de propriétés, sans code.
  • Utility bar : composants accessibles en pied d'application, comme un flow ou des notes rapides.
PiègeSi le composant n'apparaît pas dans la palette : page du mauvais type, composant non exposé ou package non installé.

Composants Lightning personnalisés (programmatique)

  • LWC : le fichier .js-meta.xml déclare <isExposed>true</isExposed> et les <targets> : lightning__RecordPage, lightning__AppPage, lightning__HomePage, lightning__FlowScreen, lightning__RecordAction, lightning__UtilityBar.
  • <targetConfigs> crée des propriétés réglables par l'admin dans Lightning App Builder.
  • Aura : interfaces flexipage:availableForAllPageTypes, flexipage:availableForRecordHome, force:hasRecordId.
  • Visualforce : s'intègre à une page Lightning, un onglet ou un bouton ; à garder pour l'existant.
  • Recommandation actuelle : LWC pour tout nouveau composant.
PiègeUn LWC déployé reste invisible dans la palette sans isExposed à true et la cible adaptée.

Actions et mises en page pour le mobile

  • Action bar mobile : actions de la section Salesforce Mobile and Lightning Experience Actions de la Page Layout, ou Dynamic Actions.
  • Compact Layout : les 4 premiers champs apparaissent sur mobile, 7 au maximum dans le panneau desktop, 10 dans l'aperçu de lookup.
  • Actions globales : menu d'actions global, mise en page Publisher Layout. Actions objet : dans le contexte du record.
  • Une action mobile doit rester courte : peu de champs, valeurs prédéfinies.
  • Lightning App Builder : aperçu Phone, facteur de forme à l'activation, et filtre de visibilité sur l'appareil.
  • Salesforce Mobile Navigation : choisit les éléments du menu. Hors ligne : Briefcase Builder.
  • Dynamic Forms et Dynamic Actions sur mobile : réglages à activer dans Salesforce Mobile App.
PiègeUn champ d'une action mobile doit être accessible en FLS, sinon il n'apparaît pas.

PiègeFormer sur des données réalistes sans payer un Full : Partial Copy, ou Developer Pro avec des données chargées.

Change sets

  • Déplacent des métadonnées entre orgs liées à la même production. L'org cible doit autoriser l'envoi : Deployment Settings → Allow Inbound Changes.
  • Outbound dans la source, upload, puis Inbound dans la cible : Validate, puis Deploy. Transaction unique : tout passe ou rien.
  • Un change set envoyé ne se modifie pas : le cloner. L'inbound se déploie en entier.
  • Ne fait pas : supprimer un composant, déployer des données, ni certains composants (valeurs de picklists standard, Sales Processes, Divisions).
  • Dépannage : View/Add Dependencies, composant manquant, profil à inclure pour la FLS. Apex en production : tests et 75 % de couverture.
  • Flow : une version active est déployée inactive par défaut. L'activer après, ou activer « Deploy processes and flows as active » avec la couverture de test requise.
PiègeImpossible entre deux orgs sans lien (production d'une autre entreprise) : package ou Metadata API.

  • Un package non géré, une fois installé, appartient à l'org : le créateur ne peut plus le faire évoluer.
  • Un package géré reste sous le contrôle de l'éditeur. La security review est requise pour une publication publique sur AgentExchange.
  • Au-delà du guide : unlocked packages pour modulariser l'existant d'une entreprise.
  • Avant de désinstaller : les données des objets du package sont supprimées, exporter si besoin.
PiègeBesoin de mises à jour poussées vers les clients : package géré. Besoin d'adapter librement le code reçu : non géré.

Plan de déploiement

  • Ordonner : dépendances d'abord (objets, champs), puis automatisations et interface, puis Permission Sets, puis données.
  • Valider avant la fenêtre : un Validate réussi permet un Quick Deploy dans les 10 jours et réduit l'indisponibilité.
  • Consigner les étapes manuelles avant et après déploiement, ce que les change sets ne couvrent pas.
  • Heures creuses, utilisateurs prévenus, sauvegarde des métadonnées. Pas de rollback automatique après un déploiement réussi.
  • Après mise en production : activer les flows, tester rapidement, former.
  • Le choix de l'outil suit le besoin : change sets pour un déploiement simple, CLI ou Lifecycle Center pour le travail en équipe avec historique, package pour distribuer.
PiègeModifier directement en production pour aller plus vite est la mauvaise réponse dans un scénario de plan de déploiement.

Ordre d'exécution à l'enregistrement

  1. Chargement de l'enregistrement et des nouvelles valeurs, validations système.
  2. Flows before-save (Fast Field Updates).
  3. Triggers before.
  4. Validations système à nouveau, puis règles de validation.
  5. Règles de doublons.
  6. Sauvegarde sans commit.
  7. Triggers after.
  8. Assignment, auto-response, escalation rules.
  9. Flows after-save (Actions and Related Records).
  10. Roll-up summary : le parent est recalculé et repasse par la sauvegarde.
  11. Partage par critères.
  12. Commit.
  13. Après le commit : e-mails, chemins asynchrones des flows.

Le jour de l'examen
  • 105 minutes pour 60 questions notées et jusqu'à 5 non notées : environ 1 min 35 par question.
  • Il faut 44 bonnes réponses sur 60. Logique et automatisation pèse 32 %, soit environ 19 questions : Flow est la priorité.
  • Chercher le mot décisif de l'énoncé : « without code », « minimal maintenance », « least privilege ».
  • Lire combien de réponses sont attendues : une question à réponses multiples n'est juste que si tout est correct.
  • Le nom d'une fonctionnalité peut varier : AppExchange ou AgentExchange, topics ou subagents, DevOps Center ou Lifecycle Center.
