Application Lifecycle Management · 8 %

ALM & méthodologies

Waterfall, Agile, hybride : choisir selon le contexte

Le cycle de vie d'une application Salesforce suit toujours les mêmes étapes. Ce qui change d'une méthodologie à l'autre, c'est la taille des lots et le nombre de passages dans la boucle.

  1. Planifier la release : besoins, priorités, calendrier.
  2. Développer : configuration et code dans des environnements isolés.
  3. Tester : tests unitaires et fonctionnels du changement.
  4. Construire la release : assembler les changements dans un environnement d'intégration.
  5. Tester la release : régression, UAT, performance sur une copie proche de la production.
  6. Livrer : déploiement en production et étapes post-déploiement.
 WaterfallScrumKanbanHybride
ExigencesFigées et validées au départBacklog qui évolueFlux de demandesCadrage initial, détail en sprints
LivraisonUne fois, à la finIncrément à chaque sprintAu fil de l'eauRelease planifiée
Bon choix quandPérimètre stable, réglementation, forfaitBesoins incertains, retours fréquentsRun, support, petites demandesBudget et date fixés, équipes agiles
Risque principalÉcarts découverts tardDérive du périmètre, dette techniquePas de jalons ni de vision d'ensembleCumuler la lourdeur des deux
Pourquoi c'est testéLes questions décrivent un client (régulé, budget fixe, besoins mouvants) et demandent la méthodologie et ses risques. La contrainte citée dans l'énoncé décide.

Gouvernance selon la maturité

Scénario type : six équipes de projet travaillent dans la même org. Elles se marchent dessus : deux frameworks de triggers différents, des mises en production le même soir, des conflits sur les mêmes objets. Il faut un cadre de gouvernance.

  • Un CoE fixe la vision et arbitre les priorités entre métiers.
  • Une Design Authority publie les standards (un seul framework de triggers, patterns d'intégration, règles déclaratif ou code) et valide les écarts.
  • Un release manager tient un calendrier de releases commun ; le CAB approuve chaque mise en production.
  • Pour une petite équipe peu mature, on commence plus léger : Git comme référence, une sandbox par personne, une validation avant production, puis on ajoute des étapes quand l'équipe grandit.
PiègeLa gouvernance la plus complète n'est pas la bonne réponse si le client n'a pas les moyens de la faire vivre. L'examen valorise une recommandation proportionnée.
Planning · 13 %

Planification

Évaluer la maturité : personnes, processus, outils

Scénario type : deux admins font leurs changements en production le vendredi soir, un consultant pousse du code par change sets, personne ne sait ce qui a été livré le mois dernier. L'architecte doit évaluer la maturité et proposer une trajectoire.

AxeFaible maturitéMaturité élevée
PersonnesPas de rôle de release manager, pas de compétence GitRôles clairs, équipe formée à Git, à la CLI et aux tests
ProcessusChangements en production, pas de revue, pas de calendrierStories avec critères d'acceptation, revue de code, CAB, calendrier
OutilsChange sets, tableurs, e-mailsBacklog outillé, Git, CI/CD, analyse statique, tests automatisés

La trajectoire se fait par étapes : source control et environnements séparés d'abord, puis validation et revue systématiques, puis automatisation (CI, tests, analyse statique), puis éventuellement packages.

Risques des environnements et mitigation

Scénario type : après le refresh de la sandbox Full, des clients réels reçoivent des e-mails de relance, et l'ERP reçoit des commandes de test sur son instance de production.

  • À la création ou au refresh, la sandbox démarre en accessibilité des e-mails System email only, et les adresses e-mail des utilisateurs reçoivent le suffixe .invalid. Les champs e-mail des contacts et des leads restent intacts : si un admin rouvre les e-mails, de vrais clients peuvent être contactés. → Masquer ou vider ces champs.
  • Les endpoints copiés depuis la production pointent vers les systèmes de production. → Les rediriger vers des environnements de test dans le runbook post-refresh.
  • Une classe qui implémente SandboxPostCopy, renseignée à la création ou au refresh, s'exécute automatiquement à la fin de la copie.
global class PostRefresh implements SandboxPostCopy {
    global void runApexClass(SandboxContext context) {
        // context.sandboxName() permet d'adapter le traitement à chaque sandbox
        Integration_Settings__c s = Integration_Settings__c.getOrgDefaults();
        s.Envoi_Actif__c = false;           // coupe les envois vers l'ERP
        upsert s;
    }
}
PiègeLe suffixe .invalid protège les utilisateurs, pas les contacts : ce n'est pas une mesure de protection des données clients.

Préparer une release Salesforce

Scénario type : l'entreprise a beaucoup d'Apex et cinq intégrations. La prochaine release Salesforce arrive dans six semaines. Comment réduire le risque ?

  1. Choisir ses sandboxes preview : vérifier leur instance (Trust, Sandbox Preview Guide) et rafraîchir avant la date limite pour être en preview, ou en non-preview.
  2. Lire les release notes et la page Release Updates : noter les mises à jour appliquées d'office et leur date.
  3. Tester : régression automatisée et processus critiques dans la sandbox preview, avec les intégrations.
  4. Activer les Release Updates d'abord en sandbox, puis en production avant leur date d'application.
  5. Geler les déploiements autour du week-end de mise à jour de l'instance de production, et communiquer les nouveautés aux utilisateurs.

Pendant la preview, développer en sandbox preview crée un décalage de version. Garder la sourceApiVersion de sfdx-project.json sur la version de la production évite de dépendre d'une API qu'elle ne connaît pas encore.

System Design · 15 %

Conception du système

Les outils agiles

Scénario type : l'auditeur demande quelles user stories sont entrées en production le 3 mars et qui les a approuvées.

  • Un outil de backlog relié au source control répond directement : la story référence ses commits (identifiant dans le message de commit ou le nom de branche), sa pull request, son approbation et son déploiement.
  • Il apporte aussi la visibilité (tableau de sprint, burndown, vélocité) et une priorisation partagée.
  • Dans Lifecycle Center, le work item passe par les statuts New, In Progress, In Review, Ready to Promote puis Promoted ; chaque passage d'étape crée une change request (pull request).

Une org ou plusieurs ?

Scénario type : un groupe acquiert une filiale qui a ses propres processus, ses administrateurs, un régulateur différent et veut garder son rythme de livraison. Le reste du groupe partage les mêmes clients et veut une vue 360°.

CritèrePousse vers une org uniquePousse vers plusieurs orgs
Clients et donnéesClients partagés, vue 360°, reporting globalClients distincts, peu de données communes
ProcessusProcessus harmonisablesProcessus très différents
RéglementationCadre communIsolation juridique ou réglementaire exigée
AutonomieGouvernance centrale acceptéeAdmins et calendrier de release propres
CoûtsUne seule plateforme à maintenirIntégrations entre orgs et artefacts dupliqués à financer

Ici, une org dédiée à la filiale, intégrée à l'org du groupe pour les données partagées, se défend. Pour le reste du groupe, l'org unique reste le choix par défaut.

Types de sandbox et stratégie

Scénario type : il faut un environnement d'UAT avec environ 3 000 comptes représentatifs et leurs opportunités, rafraîchi chaque semaine.

  • Developer et Developer Pro ne copient aucune donnée. La Full copie tout, mais ne se rafraîchit que tous les 29 jours.
  • La Partial Copy avec un sandbox template (Account, Opportunity et les objets liés) se rafraîchit tous les 5 jours et copie jusqu'à 10 000 enregistrements par objet : c'est la bonne réponse.
  • Un template ne s'utilise qu'avec une Partial Copy ou une Full. Sur une Full, il sert à exclure des objets pour accélérer la copie.
  • Clonage : créer une sandbox à partir d'une autre, pour reprendre une configuration en cours qui n'est pas encore en production.
  • Source tracking sur Developer et Developer Pro : la CLI détecte ce qui a changé dans la sandbox, comme pour une scratch org.
Pourquoi c'est testéVolume de données, fréquence de refresh et besoin de données réelles suffisent presque toujours à désigner le type de sandbox.

Outils de déploiement

Scénario type : trois profils d'équipes. Une PME de deux admins ; une équipe d'admins et de développeurs qui veut des promotions traçables sans manipuler Git ; une équipe de développeurs qui veut déployer automatiquement à chaque fusion.

  • PME : change sets acceptables au départ, avec une validation avant production. Limites : pas de suppression, pas d'historique, orgs de la même production seulement, deployment connection à autoriser dans l'org cible.
  • Équipe mixte : Lifecycle Center. Pipeline d'étapes (chaque étape = une org et une branche), work items, change requests, détection de conflits, DX Inspector pour commiter depuis la sandbox, DevOps Testing pour les quality gates.
  • Développeurs : Salesforce CLI dans une CI (GitHub Actions, GitLab CI, Jenkins…), avec validation à chaque pull request et déploiement à chaque fusion.
  • Lifecycle Center ne couvre pas tout : pas de rollback en un clic, pas de comparaison de métadonnées entre orgs, pas de backup. Les outils tiers comblent ces manques.
Building · 14 %

Construction

Branches, versions et fusions

Scénario type : Gitflow, release mensuelle. Un bug bloque les commandes en production alors que develop contient déjà des fonctionnalités inachevées de la prochaine release.

# 1. Partir de la production, pas de develop
git switch main
git switch -c hotfix/commande-bloquee

# 2. Corriger, tester, puis fusionner dans main et déployer
git switch main
git merge --no-ff hotfix/commande-bloquee
git tag v2026.10.1

# 3. Reporter le correctif dans develop
git switch develop
git merge --no-ff hotfix/commande-bloquee
  • Trunk-based : on fusionne dans main plusieurs fois par jour ; une fonctionnalité inachevée est livrée mais désactivée par un feature flag (enregistrement de Custom Metadata, Custom Permission lue avec FeatureManagement.checkPermission()).
  • Les conflits XML se réduisent avec des fusions fréquentes, des permission sets plutôt que des profils, et le format source qui découpe un objet en un fichier par champ.

Org-based ou package-based ? Scratch org ou sandbox ?

Scénario type : une entreprise veut publier séparément le module Facturation et le module Service, avec leurs propres versions, sans tout redéployer à chaque fois.

  • C'est un cas de package development : un package unlocked par module, les dépendances déclarées dans sfdx-project.json, chaque module versionné et installé indépendamment.
  • Prérequis : une Dev Hub, un découpage clair des métadonnées et une équipe à l'aise avec la CLI. Sans découpage possible, un org-dependent unlocked package laisse dépendre le package de métadonnées restées dans l'org.
  • Les scratch orgs se créent depuis un fichier de définition :
{
  "orgName": "Facturation - dev",
  "edition": "Enterprise",
  "features": ["MultiCurrency", "ServiceCloud"],
  "settings": {
    "lightningExperienceSettings": { "enableS1DesktopEnabled": true }
  }
}

Org Shape remplace la liste des features et settings par la « forme » d'une org existante (édition, licences, réglages). Un snapshot capture une scratch org déjà configurée pour en recréer d'autres rapidement.

PiègeLes scratch orgs ne remplacent pas les sandboxes : l'intégration, l'UAT et les problèmes liés aux données réelles demandent une sandbox.

Tests unitaires et données de test

Une seule classe de test peut couvrir les quatre familles de cas attendues à l'examen.

@IsTest
private class RemiseServiceTest {
    @TestSetup static void setup() { TestFactory.comptes(200); }   // gros volume

    @IsTest static void remiseAppliquee() {                         // positif
        Opportunity o = TestFactory.opportunite(20);
        insert o;
        Assert.areEqual(20, [SELECT Remise__c FROM Opportunity WHERE Id = :o.Id].Remise__c);
    }

    @IsTest static void remiseTropForteRefusee() {                  // négatif
        try {
            insert TestFactory.opportunite(60);
            Assert.fail('La règle de validation aurait dû bloquer');
        } catch (DmlException e) {
            Assert.isTrue(e.getMessage().contains('Remise'));
        }
    }

    @IsTest static void commercialSansDroit() {                      // permissions
        User u = TestFactory.utilisateur('Commercial junior');
        System.runAs(u) {
            Assert.isFalse(RemiseService.peutAccorder(30));
        }
    }
}
PiègeSystem.runAs() applique le partage d'enregistrements de l'utilisateur, pas ses permissions d'objet ni sa sécurité au niveau des champs. Pour tester ces droits, le code testé doit s'exécuter en mode utilisateur.

Qualité du code

Scénario type : chaque release apporte son lot de SOQL dans des boucles et de classes sans tests. L'architecte doit empêcher ce code d'atteindre develop.

  1. Standards écrits : nommage, framework de triggers, gestion des erreurs, règles déclaratif ou code.
  2. Pull request obligatoire sur develop et main, avec au moins une revue par un pair.
  3. Contrôles automatiques sur chaque pull request : Code Analyzer v5, validation du déploiement avec tests, couverture.
  4. Seuils bloquants : la fusion est refusée si un contrôle échoue.
  5. Suivi en production : ApexGuru signale les anti-patterns observés à l'exécution.
# Analyse statique dans la CI
sf code-analyzer run --rule-selector Recommended --output-file resultats.html
Deploying · 14 %

Déploiement

Metadata API vs Tooling API

Règle simple : déplacer de la configuration entre orgs → Metadata API ; construire un outil de développement ou interroger des métadonnées fines (couverture, logs, symboles) → Tooling API.

<!-- package.xml : le joker ne couvre pas les objets standard -->
<Package xmlns="http://soap.sforce.com/2006/04/metadata">
    <types>
        <members>*</members>          <!-- objets personnalisés -->
        <members>Account</members>    <!-- objet standard, à nommer -->
        <name>CustomObject</name>
    </types>
    <version>66.0</version>
</Package>
-- Tooling API : couverture par classe ou trigger
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate
  • Un déploiement de plus de 10 000 fichiers ou de plus de 39 Mo compressés se découpe en plusieurs déploiements.
  • Retrieve d'un profil seul : il revient presque vide. Le récupérer avec les objets, champs et classes concernés, ou passer aux permission sets.
  • Avant d'automatiser un type de métadonnée, vérifier dans le Metadata Coverage Report qu'il est supporté ; sinon, il rejoint le runbook manuel.

Étapes avant et après déploiement

Scénario type : la release supprime le champ Ancien_Statut__c, que la classe CommandeService référence encore, et active un nouveau flow.

  1. J-1, validation : sf project deploy validate avec la classe corrigée (sans référence au champ), le flow, et destructiveChangesPost.xml qui supprime le champ.
  2. Étapes « pré » : désactiver les intégrations si besoin, activer « Defer Sharing Calculations » pour une grosse modification de partage, prévenir les utilisateurs.
  3. Jour J : sf project deploy quick --job-id … dans les 10 jours qui suivent la validation, sans relancer les tests.
  4. Étapes « post » : activer le flow si le réglage « Deploy processes and flows as active » n'est pas coché, attribuer les permission sets, saisir les secrets des External Credentials, replanifier les jobs Apex, charger les données de référence, smoke test.
  • destructiveChangesPre.xml sert quand le composant doit disparaître avant que le reste soit déployé, par exemple pour libérer un nom.
  • Un déploiement qui modifie une classe référencée par un job Apex planifié échoue, sauf si le réglage de déploiement qui l'autorise est activé. Sinon : supprimer le job, déployer, replanifier.
PiègeUn quick deploy ne relance pas les tests : c'est tout son intérêt pour réduire la fenêtre de mise en production.

Données de référence techniques

Scénario type : des règles de tarification sont stockées dans un objet personnalisé avec une hiérarchie parent-enfant. Elles doivent arriver dans chaque environnement avec chaque release.

  • Si la logique le permet, les transformer en Custom Metadata Types : ils suivent les métadonnées dans Git et dans les déploiements.
  • Sinon, les stocker dans le repo et les charger par upsert sur un External ID, en commençant par les parents, les enfants retrouvant leur parent par l'External ID.
# Parents puis enfants, rejouable à chaque release sans doublon
sf data upsert bulk --sobject Regle_Prix__c --file data/regles.csv --external-id Code__c --target-org uat
sf data upsert bulk --sobject Palier_Prix__c --file data/paliers.csv --external-id Code__c --target-org uat
# paliers.csv référence le parent par sa clé : Regle_Prix__r.Code__c
PiègeUne copie de sandbox conserve les Id de la production, mais deux orgs indépendantes (production et scratch org, par exemple) n'ont jamais les mêmes Id. Une clé métier stable est la seule référence sûre.

Exécution des tests et couverture

Scénario type : le déploiement ne contient que deux classes et leurs classes de test. L'équipe veut un déploiement rapide en production sans exécuter les 3 000 tests de l'org.

sf project deploy start --source-dir force-app/main/default/classes \
  --test-level RunSpecifiedTests --tests FactureServiceTest --tests AvoirServiceTest \
  --target-org prod
  • Avec RunSpecifiedTests, chacune des deux classes déployées doit être couverte à 75 % par les tests listés ; la couverture globale de l'org n'est pas le critère.
  • Sans niveau précisé, un déploiement en production qui contient de l'Apex exécute RunLocalTests.
  • Les tests Apex s'exécutent en parallèle. Des tests qui modifient les mêmes enregistrements (ou un même Custom Setting) peuvent échouer par verrouillage : « Disable Parallel Apex Testing » les exécute un par un.
Pourquoi c'est testéLa différence entre 75 % global (RunLocalTests) et 75 % par composant (RunSpecifiedTests) revient souvent.

Stratégie de données de test

Scénario type : une banque veut des sandboxes d'UAT réalistes, mais aucune donnée client réelle ne doit en sortir.

  1. Copier : Partial Copy avec un template, ou Full selon le volume.
  2. Masquer immédiatement après le refresh, avant d'ouvrir l'accès (Data Mask & Seed : anonymisation, pseudonymisation, suppression).
  3. Compléter par des jeux de données de référence versionnés et rejouables (seed templates, plans de données).
  4. Réserver l'accès aux utilisateurs qui en ont besoin, et tracer les refresh.

Pour les sandboxes Developer et Developer Pro, qui ne copient aucune donnée, le seeding apporte les données de test. Data Mask & Seed alimente les quatre types de sandbox.

Releasing · 13 %

Releases

Managé, non managé ou unlocked ?

Trois scénarios, trois réponses.

  • Un intégrateur veut partager un modèle d'application que chaque client adaptera librement, sans suivi des versions : non managé.
  • Une entreprise veut découper son org en modules versionnés, avec des dépendances, et garder la main sur le code : unlocked.
  • Un éditeur vend une application sur l'AppExchange, protège son code et pousse les correctifs à ses clients : managé 2GP.
// sfdx-project.json : le package Service dépend du package Core
{
  "packageDirectories": [
    { "path": "core", "package": "Core", "versionNumber": "1.4.0.NEXT", "default": false },
    { "path": "service", "package": "Service", "versionNumber": "2.1.0.NEXT", "default": true,
      "dependencies": [ { "package": "Core", "versionNumber": "1.4.0.LATEST" } ] }
  ],
  "namespace": "",
  "sourceApiVersion": "66.0"
}

Installation : le package de base (Core) d'abord, puis ceux qui en dépendent. Une version bêta s'installe en scratch org et en sandbox ; seule une version promue s'installe en production.

Plan de release et sandboxes

Scénario type : deux streams en parallèle (CRM et Service), une release mensuelle, une équipe de formation, et des correctifs urgents possibles à tout moment.

  • Stream CRM : sandboxes Developer pour chaque développeur → Developer Pro d'intégration CRM.
  • Stream Service : même schéma, avec sa propre Developer Pro d'intégration.
  • Convergence : une Partial Copy de QA commune où les deux streams sont fusionnés, puis l'UAT, puis une Full de staging qui répète le déploiement de production.
  • Formation : une Partial Copy rafraîchie après chaque release, avec ses données de démonstration.
  • Hotfix : une Developer Pro rafraîchie depuis la production, hors du flux des streams.

Après chaque release, toutes les branches et sandboxes de développement repartent de la nouvelle version de production (back-merge et refresh), sinon les écarts s'accumulent.

Stratégie de release management

Une stratégie de release répond à quatre questions : quand, quoi, comment, et comment revenir en arrière.

QuestionRéponse attendue
QuandCalendrier publié : majeures planifiées, mineures régulières, hotfix ; pas pendant le week-end de mise à jour Salesforce
QuoiContenu figé par le release manager, stories tracées jusqu'aux commits, release notes internes
CommentValidation la veille, quick deploy, étapes du runbook, smoke test, go/no-go au CAB
Retour arrièreRedéployer le tag Git précédent, désactiver par feature flag ; pas de rollback natif
PiègeLa livraison continue n'est pas une recommandation par défaut : elle demande des tests automatisés fiables et une équipe mature.
Operating · 10 %

Exploitation

Changer directement en production

Scénario type : pour débloquer une équipe commerciale, un admin a modifié une règle de validation en production. Deux semaines plus tard, la release suivante remet l'ancienne version.

  • Le repo contenait encore l'ancienne règle : le déploiement l'a réécrite. C'est la conséquence directe de la dérive entre la production et le source control.
  • Le bon réflexe, juste après le changement : retrieve de la règle depuis la production, commit sur main, fusion dans develop et dans les branches en cours, mise à jour des sandboxes. Lifecycle Center propose un back-sync pour ramener ces changements.
  • Setup Audit Trail (180 jours, export possible) retrouve ces changements a posteriori.
  • Pour éviter que cela se reproduise : définir les changements autorisés en production et le processus d'urgence, et retirer « Customize Application » aux profils qui n'en ont pas besoin.

Hotfix, refresh et supervision

  1. Reproduire le bug dans la sandbox de hotfix, rafraîchie depuis la production.
  2. Corriger sur une branche hotfix/* partie de main, avec un test qui prouve la correction.
  3. Approuver par le circuit d'urgence (CAB restreint).
  4. Déployer en production avec RunSpecifiedTests ou RunLocalTests, puis smoke test.
  5. Réintégrer : fusion dans main et develop, propagation aux sandboxes.

Supervision après une release : e-mails d'exception Apex, debug logs ciblés, Event Monitoring, Scale Center pour les lenteurs et les verrous, Setup Audit Trail pour les changements de configuration.

Artefacts communs à plusieurs orgs

Scénario type : quatre orgs internes partagent un framework de journalisation, un framework de triggers et des utilitaires d'intégration. Chaque org a aussi sa logique propre.

ApprocheAvantageLimite

Un repo, un manifeste par orgSimple, un seul historiqueDépendances implicites, risque d'écraser une spécificité
