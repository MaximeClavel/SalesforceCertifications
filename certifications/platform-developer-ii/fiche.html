Advanced Developer Fundamentals · 15 %

Fondamentaux avancés

Multi-devises et localisation, partage programmatique, configuration par métadonnées.

0/3
Objectifs officiels de la section
  • Connaître les fonctionnalités de localisation et de multi-devises, et leur impact sur le code.
  • Justifier, selon un scénario, l'usage des objets de partage et de l'Apex managed sharing.
  • Connaître les bonnes pratiques des Custom Metadata Types et des Custom Settings, et savoir les mettre en œuvre.

Multi-devises & localisation

  • En multi-devises, chaque enregistrement porte un champ CurrencyIsoCode. convertCurrency(Amount) dans le SELECT convertit dans la devise de l'utilisateur ; FORMAT() met en forme selon sa locale. On les combine : FORMAT(convertCurrency(Amount)).
  • Dans un WHERE, préfixer le montant par le code ISO : WHERE Amount > USD5000. Sans code, c'est le nombre brut qui est comparé.
  • Avec GROUP BY ou HAVING, les agrégats (SUM, MAX…) sont renvoyés dans la devise de l'org, et convertCurrency() ne s'applique pas à un agrégat.
  • Advanced Currency Management : taux datés (DatedConversionRate) pour Opportunity, OpportunityLineItem et l'historique d'opportunité ; convertCurrency() prend le taux de la date concernée (ex. CloseDate).
  • Localisation : les Datetime sont stockés en GMT ; maDate.format() les affiche dans le fuseau et la locale de l'utilisateur. Textes traduits avec les Custom Labels (System.Label.X, @salesforce/label/c.X en LWC) et toLabel(Champ) pour les valeurs de picklist.
PiègeComparer en Apex les montants de deux enregistrements dans des devises différentes, sans conversion, donne un résultat faux.

Partage programmatique (Apex managed sharing)

  • Un objet dont l'OWD est Private ou Public Read Only a un objet de partage : AccountShare, OpportunityShare, Projet__Share… Chaque ligne indique l'enregistrement, l'utilisateur ou le groupe (UserOrGroupId), le niveau (AccessLevel : Read ou Edit) et la raison (RowCause).
  • Sur un objet personnalisé, une Apex Sharing Reason (Schema.Projet__Share.RowCause.Chef_de_projet__c) rend le partage durable : il survit au changement de propriétaire. Un partage RowCause = 'Manual' est supprimé quand le propriétaire change.
  • Les Apex Sharing Reasons n'existent que sur les objets personnalisés. Sur Account ou Opportunity, on recrée le partage manuel, par exemple dans un trigger qui détecte le changement de propriétaire.
  • Recalcul : une classe Database.Batchable déclarée pour l'objet dans « Apex Sharing Recalculation » recrée les partages, par exemple après un changement d'OWD.
  • Un partage ne peut qu'ouvrir l'accès au-delà de l'OWD, jamais le restreindre.
PiègeN'utiliser l'Apex managed sharing que si aucune Sharing Rule, par propriétaire ou par critères, ne peut exprimer la logique.

Custom Metadata Types vs Custom Settings

  • Custom Metadata Type : les enregistrements sont des métadonnées, donc déployables et packageables. Lecture avec getAll() / getInstance(), sans requête SOQL. Utilisables dans les formules, les règles de validation et les Flows. Pas de DML : en Apex, on les modifie avec Metadata.Operations.enqueueDeployment(), de façon asynchrone.
  • Custom Setting Hierarchy : une valeur par défaut pour l'org, surchargée par profil puis par utilisateur ; getInstance() renvoie la valeur la plus spécifique. DML autorisé, et lisible dans les formules via $Setup.
  • Custom Setting List : un Custom Metadata Type est en général préférable.
  • Les valeurs d'un Custom Setting sont des données : elles ne se déploient pas par change set et sont invisibles dans les tests tant qu'on ne les crée pas. Les enregistrements de Custom Metadata sont visibles dans les tests.

Automatisation, logique & intégration

Déclaratif et code ensemble, triggers, Apex asynchrone et dynamique, Platform Events, gestion d'erreurs et intégrations.

0/7
Objectifs officiels de la section
  • Analyser les interactions entre plusieurs automatisations, déclaratives et programmatiques, et justifier la solution optimale.
  • Déterminer les bénéfices de l'Apex asynchrone pour un besoin donné.
  • Choisir la fonctionnalité d'Apex dynamique adaptée.
  • Choisir la logique de publication et d'abonnement des Platform Events.
  • Utiliser les fonctionnalités Apex de gestion d'erreurs et d'intégrité transactionnelle.
  • Appliquer les techniques d'intégration entrante et sortante.

Déclaratif ou code : qui s'exécute quand ?

  • Flow est l'outil déclaratif de référence. Workflow Rules et Process Builder ne sont plus supportés depuis le 31 décembre 2025 : ils continuent de s'exécuter, mais sans support ni correctifs.
  • Ordre officiel : Flows before-save → triggers before → règles de validation → duplicate rules → sauvegarde → triggers after → assignment rules → … → Flows after-save → entitlement rules → roll-up summary → partage par critères → commit. Détail dans Repères.
  • Un Flow before-save met à jour l'enregistrement sans DML. Un Flow after-save qui modifie l'enregistrement déclencheur provoque un nouvel enregistrement, donc un nouveau passage dans les triggers.
  • Plusieurs Flows sur le même objet s'ordonnent avec leur trigger order ; plusieurs triggers Apex sur le même objet et le même contexte n'ont pas d'ordre garanti.
  • Passerelles : @InvocableMethod expose de l'Apex aux Flows ; Apex lance un Flow avec Flow.Interview.
PiègeSi un Flow before-save et un trigger before modifient le même champ, le trigger s'exécute après le Flow : c'est sa valeur qui reste.

Triggers : bonnes pratiques

  • Un seul trigger par objet, sans logique métier : il délègue à une classe handler, par exemple avec un switch on Trigger.operationType.
  • Bulkifier : collections, une seule requête avec IN, des Map ; jamais de SOQL ni de DML dans une boucle.
  • Bloquer un enregistrement avec record.addError('message'), ou sur un champ précis ; le message s'affiche dans l'interface.
  • Récursion : garde statique (un Set<Id> des enregistrements déjà traités) ; profondeur maximale 16.
  • Depuis Summer '26, les triggers s'exécutent toujours en mode système et ne peuvent pas déclarer de mode de partage ou d'accès : on définit ces modes dans les classes handler.
trigger OpportunityTrigger on Opportunity (before insert, before update, after update) {
    switch on Trigger.operationType {
        when BEFORE_INSERT { OpportunityHandler.beforeInsert(Trigger.new); }
        when BEFORE_UPDATE { OpportunityHandler.beforeUpdate(Trigger.new, Trigger.oldMap); }
        when AFTER_UPDATE  { OpportunityHandler.afterUpdate(Trigger.newMap, Trigger.oldMap); }
    }
}

Apex asynchrone : bénéfices et choix

  • Bénéfices : limites plus hautes (200 SOQL, 60 s de CPU, 12 Mo de heap), callouts hors de la transaction de l'utilisateur, gros volumes, découplage.
  • Future : simple ; paramètres primitifs ; pas de suivi ; impossible depuis un batch ou une autre méthode future.
  • Queueable : sObjects en paramètre, Id de job, chaînage (un job enfant depuis un job). AsyncOptions : délai de 0 à 10 min, profondeur de chaîne maximale, signature anti-doublon (QueueableDuplicateSignature). Un Transaction Finalizer (System.attachFinalizer) réagit à la réussite ou à l'échec du job.
  • Batch : jusqu'à 50 millions d'enregistrements avec un QueryLocator, scope de 200 par défaut (2 000 max), Database.Stateful pour garder un état ; 5 batchs actifs et 100 en attente (flex queue).
  • Scheduled : expression CRON, 100 jobs planifiés au maximum.
  • Apex Cursors, GA en API 66.0 (Spring '26) : Database.getCursor() puis fetch(position, nombre), jusqu'à 50 millions de lignes, transmis d'un Queueable au suivant.
AsyncOptions options = new AsyncOptions();
options.MinimumQueueableDelayInMinutes = 5;   // de 0 à 10
options.MaximumQueueableStackDepth = 10;      // garde-fou pour une chaîne de jobs
System.enqueueJob(new SyncAccountJob(accountId), options);
PiègeUne méthode @future n'accepte pas de sObject en paramètre et ne peut pas être appelée depuis un Batch Apex ni depuis une autre méthode @future.

Apex dynamique

  • Describe : Schema.SObjectType.Account.fields.Name.isUpdateable(), Schema.describeSObjects(). Schema.getGlobalDescribe() est coûteux : le mettre en cache.
  • SOQL dynamique : Database.query(), ou Database.queryWithBinds(requête, binds, AccessLevel) qui lie les variables par nom et précise le mode d'accès.
  • DML dynamique : SObjectType.newSObject(), record.put('Champ__c', valeur) et get().
  • Instanciation dynamique : Type.forName('NomClasse').newInstance() avec une interface (patterns stratégie et factory) ; interface Callable pour un couplage faible.
Map<String, Object> binds = new Map<String, Object>{ 'stage' => stageName };
List<Opportunity> opps = Database.queryWithBinds(
    'SELECT Id, Name FROM Opportunity WHERE StageName = :stage',
    binds,
    AccessLevel.USER_MODE
);

Platform Events & Change Data Capture

  • Publier : EventBus.publish() (les limites DML s'appliquent), Flow ou API. Publish After Commit : publié seulement si la transaction est validée. Publish Immediately : publié tout de suite, même si la transaction échoue ensuite, sans rollback possible.
  • Les événements créés depuis l'API 45.0 sont high-volume, conservés 72 h. Les anciens standard-volume sont legacy : retrait prévu en Summer '27.
  • S'abonner dans Salesforce : trigger after insert (seul contexte, exécuté par l'utilisateur Automated Process ; PlatformEventSubscriberConfig change l'utilisateur et la taille de lot), Flow déclenché par Platform Event, LWC avec lightning/empApi.
  • S'abonner depuis l'extérieur : Pub/Sub API (gRPC), recommandée. La Streaming API CometD fonctionne toujours, mais PushTopic et les generic events sont legacy.
  • Fiabilité : EventBus.RetryableException pour réessayer un lot, setResumeCheckpoint() pour reprendre après une erreur, callbacks de publication Apex pour suivre le résultat.
  • CDC : événements automatiques (création, modification, suppression, restauration) sur les objets activés, canaux …__ChangeEvent, en-tête ChangeEventHeader, rejouables pendant 72 h.

Gestion des erreurs & intégrité transactionnelle

  • Database.insert(records, false) : succès partiel, erreurs ligne par ligne dans Database.SaveResult. Un DML classique annule tout le lot à la première erreur.
  • Database.setSavepoint() / Database.rollback(sp) : annule les DML faits après le savepoint, sans rendre les limites consommées.
  • Exceptions personnalisées (extends Exception), try / catch / finally. Une exception non interceptée annule toute la transaction.
  • System.LimitException ne peut pas être interceptée : on surveille la consommation avec la classe Limits.
  • En asynchrone : Transaction Finalizer sur un Queueable, EventBus.RetryableException dans un trigger d'événement. Vers l'interface : AuraHandledException.
PiègeMIXED_DML_OPERATION : un DML sur un objet de configuration (User, Group, PermissionSetAssignment…) et un DML sur un objet métier dans la même transaction. On les sépare avec @future, ou avec System.runAs() dans un test.

Intégration sortante & entrante

  • Sortant : Http, HttpRequest, HttpResponse avec une Named Credential (callout:Nom/chemin), sans Remote Site Setting. Modèle actuel : la Named Credential porte l'URL, l'External Credential porte l'authentification et ses principals, accordés via des permission sets. Les « legacy named credentials » sont dépréciées.
  • Pas de callout après un DML non validé dans la même transaction (« uncommitted work pending ») ; depuis un trigger, toujours en asynchrone (@future(callout=true), ou Queueable avec Database.AllowsCallouts).
  • Limites : 100 callouts et 120 s cumulées par transaction ; timeout de 10 s par défaut, 120 s au maximum.
  • SOAP sortant : classes générées par « Generate from WSDL ». API décrites en OpenAPI : External Services, appelables depuis Flow et Apex. Sans code : action Outbound Message dans un Flow after-save.
  • Entrant : API REST, SOAP, Bulk API 2.0 (gros volumes) et Composite ; services Apex REST (@RestResource) et Apex SOAP (méthodes webservice) ; Pub/Sub API pour publier des événements.
User Interface · 20 %

Interface utilisateur

LWC, Aura et Visualforce avec leur contrôleur Apex : événements, erreurs, responsive et static resources.

0/8
Objectifs officiels de la section
  • Analyser le code d'un LWC ou d'un composant Aura et de son contrôleur Apex, et déterminer les changements nécessaires.
  • Utiliser Visualforce pour des actions, des rafraîchissements partiels et des opérations asynchrones.
  • Appliquer les bonnes pratiques d'affichage des erreurs.
  • Choisir entre LWC, Aura et Visualforce et en justifier les bénéfices.
  • Rendre un composant responsive selon le form factor.
  • Communiquer par événements entre LWC ou composants Aura.
  • Connaître l'intérêt des static resources dans Visualforce, LWC et Aura.

LWC et contrôleur Apex

  • Méthode @AuraEnabled static. cacheable=true est obligatoire pour @wire et interdit le DML ; l'appel impératif (Promise) sert aux modifications.
  • Les paramètres sont passés dans un objet dont les clés sont les noms des paramètres Apex ; '$prop' rend un paramètre de wire réactif ; le wire fournit { data, error }.
  • Après une modification faite hors de Lightning Data Service : refreshApex(valeurWire) et notifyRecordUpdateAvailable(recordIds), qui remplace getRecordNotifyChange (déprécié).
  • Sécurité du contrôleur : with sharing ou inherited sharing, requêtes WITH USER_MODE (défaut en API 67.0), Security.stripInaccessible() pour retirer les champs non lisibles.
  • Lightning Data Service (lightning-record-form, getRecord, updateRecord) : pas d'Apex, FLS et partage appliqués, cache partagé entre composants.

Les bases LWC qui reviennent dans les questions

  • Cycle de vie : constructor() → connectedCallback() (à chaque insertion dans le DOM) → rendu → renderedCallback() (après chaque rendu : le protéger par un drapeau) ; disconnectedCallback() ; errorCallback() capture les erreurs des composants enfants.
  • Décorateurs : @api (public), @wire ; @track seulement pour suivre les mutations internes d'un objet ou d'un tableau.
  • Directives : lwc:if, lwc:elseif et lwc:else remplacent if:true et if:false, déconseillés ; for:each avec key ; lwc:ref pour cibler un élément.
  • Côté navigateur, Lightning Web Security remplace progressivement Lightning Locker ; c'est le réglage par défaut des orgs créées depuis Winter '23.

Visualforce : actions, rafraîchissement partiel, asynchrone

  • rerender sur apex:commandButton ou apex:commandLink : seuls les composants ciblés sont rafraîchis.
  • apex:actionFunction (appeler une action depuis du JavaScript), apex:actionSupport (sur un événement DOM), apex:actionPoller (à intervalle régulier), apex:actionStatus (indicateur), apex:actionRegion (limiter ce qui est soumis).
  • JavaScript Remoting : méthode @RemoteAction static, appel asynchrone sans view state.
  • Callout long : Continuation.
  • Contrôleurs : standard, extension (constructeur qui reçoit un ApexPages.StandardController), personnalisé ; StandardSetController pour paginer, jusqu'à 10 000 enregistrements.

Afficher les erreurs

  • D'Apex vers le composant : lever une AuraHandledException avec un message destiné à l'utilisateur ; côté JavaScript, lire error.body.message (les erreurs de l'UI API peuvent arriver sous forme de tableau).
  • Notification : le module lightning/toast (Toast.show()) est recommandé ; ShowToastEvent n'est pas supporté dans les sites LWR.
  • Erreurs de saisie : setCustomValidity() puis reportValidity() sur un lightning-input ; lightning-messages dans un lightning-record-edit-form.
  • errorCallback() joue le rôle d'« error boundary » pour les composants enfants.
  • Triggers : addError(). Visualforce : ApexPages.addMessage() et <apex:pageMessages/>.

Choisir LWC, Aura ou Visualforce

  • LWC par défaut : standards web, meilleures performances, Lightning Web Security.
  • Un composant Aura peut contenir des LWC, l'inverse est impossible : Aura reste pertinent pour l'existant.
  • Visualforce : rendu PDF (renderAs="pdf"), pages et e-mails existants, Salesforce Classic.
  • Lightning Out pour afficher des composants hors de Salesforce ; LWR pour des sites Experience Cloud rapides.

Responsive selon le form factor

  • lightning-layout et lightning-layout-item (size, small-device-size, medium-device-size, large-device-size), et la grille SLDS.
  • import FORM_FACTOR from '@salesforce/client/formFactor' : Large (bureau), Medium (tablette), Small (téléphone).
  • Dans le .js-meta.xml, <supportedFormFactors> (Large, Small) déclare les form factors pris en charge par les pages d'application et d'enregistrement dans App Builder.
  • En Aura : $Browser.formFactor.

Communication par événements

  • Parent → enfant : propriétés et méthodes @api.
  • Enfant → parent : this.dispatchEvent(new CustomEvent('select', { detail })), écouté avec onselect. Nom en minuscules, sans tiret.
  • bubbles: true fait remonter l'événement, composed: true lui fait franchir le shadow DOM ; les deux valent false par défaut.
  • Composants sans lien : Lightning Message Service (canal de message), aussi entre LWC, Aura et Visualforce.
  • Aura : l'événement de composant remonte la hiérarchie ; l'événement d'application est diffusé à tous les abonnés, à utiliser avec parcimonie.

Static resources

  • Fichiers JS, CSS, images ou archives zip stockés dans l'org (5 Mo par ressource), mis en cache par le navigateur et déployés avec les métadonnées.
  • LWC : import LIB from '@salesforce/resourceUrl/lib', puis loadScript() ou loadStyle() de lightning/platformResourceLoader, une seule fois.
  • Visualforce : {!$Resource.logo}, ou {!URLFOR($Resource.assets, 'img/logo.png')} pour un fichier dans un zip.
  • Aura : <ltng:require scripts="{!$Resource.lib}"/>.
  • Intérêt : pas de dépendance à un CDN externe (CSP), versions maîtrisées, mise en cache.

Tests, débogage & déploiement

Mocks et stubs, tests du front, diagnostic et déploiement piloté par les sources.

0/4
Objectifs officiels de la section
  • Appliquer des techniques avancées de test Apex, comme les mocks et les stubs.
  • Tester et déboguer les LWC, les composants Aura, les contrôleurs Visualforce et le JavaScript.
  • Trouver la cause d'un code, d'un trigger ou d'un test Apex qui ne se comporte pas comme prévu.
  • Définir le processus de déploiement, ses outils et le développement piloté par les sources.

Tests Apex avancés : mocks et stubs

  • Callouts : HttpCalloutMock avec Test.setMock(), StaticResourceCalloutMock, MultiStaticResourceCalloutMock ; SOAP : WebServiceMock.
  • Stub API : implémenter System.StubProvider et créer le double avec Test.createStub(Type, provider) ; pas pour les méthodes statiques.
  • SOSL renvoie une liste vide en test : définir le résultat avec Test.setFixedSearchResults(ids).
  • Platform Events délivrés au Test.stopTest() ou avec Test.getEventBus().deliver() ; CDC activé avec Test.enableChangeDataCapture().
  • Données : @testSetup (une méthode par classe), TestDataFactory, Test.loadData(). Test.startTest() / stopTest() réinitialise les limites et exécute l'asynchrone. System.runAs() applique le partage de l'utilisateur, pas sa FLS.
  • Couverture : 75 % sur l'org, plus de 0 % pour chaque trigger, tous les tests au vert.

Tester et déboguer le front

  • LWC : Jest via @salesforce/sfdx-lwc-jest, en local avec Node.js, sans org ; createElement pour monter le composant, jest.mock() pour l'Apex, emit() pour simuler un wire.
  • Aura : Lightning Testing Service (Jasmine ou Mocha). Jest ne fonctionne qu'avec les LWC.
  • Contrôleurs Visualforce : test Apex avec Test.setCurrentPage(Page.MaPage), ApexPages.currentPage().getParameters().put('id', …) et new ApexPages.StandardController(record).
  • JavaScript : mode debug Lightning (code non minifié), points d'arrêt ou instruction debugger; dans les DevTools du navigateur.

Trouver pourquoi le code ne fait pas ce qui est prévu

  • Debug logs et trace flags (utilisateur, classe, trigger) ; pour un trigger de Platform Event, poser le trace flag sur l'entité Automated Process.
  • Log Inspector (Execution Overview, Timeline, Executed Units) ; Apex Replay Debugger dans VS Code pour rejouer un log avec des points d'arrêt ; checkpoints dans la Developer Console.
  • La Web Console (bêta depuis avril 2026) remplace progressivement la Developer Console : logs, SOQL, Query Plan, Anonymous Apex.
  • Classe Limits (getQueries(), getCpuTime()…), System.debug(LoggingLevel.ERROR, …). Un log est limité à 20 Mo : au-delà, les lignes les plus anciennes sont retirées.

Déploiement et développement piloté par les sources

  • Salesforce CLI (sf) : sf project deploy start, sf project retrieve start, sf project deploy validate puis sf project deploy quick ; suivi des sources avec les scratch orgs (Dev Hub) et les sandboxes compatibles.
  • Packages 2GP : unlocked (modules internes, code visible) ou managed (AppExchange, code protégé). DevOps Center pour un pipeline Git guidé.
  • Change sets : uniquement entre orgs liées, sans suppression possible ; on supprime avec destructiveChanges.xml (Metadata API). L'Ant Migration Tool est retiré depuis Spring '24.
  • Niveaux de test : RunLocalTests (défaut en production quand il y a de l'Apex), RunSpecifiedTests (chaque classe et trigger déployé couvert à 75 %), RunAllTestsInOrg, NoTestRun (hors production), RunRelevantTests (bêta Spring '26).
Performance · 18 %

Performance

Interfaces rapides, requêtes sur gros volumes, callouts asynchrones, réutilisation et code inefficace.

0/5
Objectifs officiels de la section
  • Identifier les problèmes de performance courants des interfaces et les techniques pour les corriger.
  • Choisir la logique et la structure de requête adaptées aux gros volumes de données.
  • Déterminer les gains de performance d'un callout asynchrone.
  • Identifier les cas de réutilisation de code et la façon de la mettre en œuvre.
  • Repérer les inefficacités d'un code et les corriger.

Performance de l'interface

  • Moins d'allers-retours serveur : Lightning Data Service (cache partagé), méthodes Apex cacheable=true, uniquement les champs utiles.
  • Charger à la demande : lwc:if pour ne rendre qu'au besoin, lightning-datatable avec enable-infinite-loading et onloadmore, pagination côté serveur.
  • Pas de traitement lourd dans renderedCallback(), appelé après chaque rendu.
  • Visualforce : view state limité à 170 Ko (variables transient) ; readOnly="true" sur apex:page (1 million de lignes, 10 000 éléments par itération, pas de DML) ; JavaScript Remoting sans view state.
  • Static resources mises en cache plutôt que des fichiers rechargés à chaque page.

Requêtes et gros volumes (LDV)

  • Un filtre est sélectif quand un index peut le servir. Indexés par défaut : Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId, lookups et master-detail, champs External ID et Unique. Index personnalisé : via le Support.
  • Seuils : index standard 30 % du premier million puis 15 % (plafond 1 000 000) ; index personnalisé 10 % puis 5 % (plafond 333 333).
  • En général non sélectifs : !=, NOT, LIKE '%texte', comparaison à null, formules non déterministes. Vérifier avec le Query Plan (coût inférieur à 1).
  • Traitements de masse : SOQL for loop (lots de 200, heap réduit), Batch Apex (QueryLocator, 50 M), Apex Cursors, Bulk API 2.0. OFFSET est limité à 2 000 lignes.
  • Data skew : plus de 10 000 enregistrements enfants sous un même parent, ou détenus par un même propriétaire, provoquent des verrous (UNABLE_TO_LOCK_ROW) et des recalculs de partage lents.
  • Big Objects : Async SOQL est retiré depuis Summer '23 ; on interroge en SOQL en filtrant sur l'index, dans l'ordre, ou via Batch Apex et Bulk API. Skinny tables : activées par le Support.

Callouts asynchrones et performance

  • Une requête synchrone de plus de 5 secondes compte dans la limite d'org de requêtes longues simultanées (10) : des callouts lents peuvent bloquer d'autres utilisateurs.
  • Continuation (Visualforce, Aura, LWC) : le thread serveur est libéré pendant l'attente ; 3 callouts et 120 s au maximum ; pas de DML dans la méthode qui renvoie la Continuation, mais possible dans le callback. En LWC : @AuraEnabled(continuation=true).
  • Sans attente de l'utilisateur : Queueable avec Database.AllowsCallouts, chemin asynchrone d'un Flow, ou Platform Event traité par un autre système.

Réutiliser le code

  • Apex : classes de service et utilitaires, interfaces, classes virtual et abstract, framework de trigger handler, couches Selector / Domain / Service, logique pilotée par Custom Metadata, @InvocableMethod partagée avec les Flows.
  • LWC : module JavaScript de service (composant sans template qui exporte des fonctions), composition, composants de base, canaux LMS partagés.
  • Aura : héritage (extends, composants abstraits). Visualforce : apex:component et templates (apex:composition).
  • Tests : une TestDataFactory commune.

Repérer les inefficacités

  • SOQL ou DML dans une boucle → une requête avec IN, un DML sur une liste.
  • Boucles imbriquées pour rapprocher deux listes → Map indexée par Id.
  • Requêtes répétées ou trop larges → ne lire que les champs et lignes utiles, réutiliser le résultat.
  • Schema.getGlobalDescribe() appelé plusieurs fois → le mettre en cache dans une variable statique.
  • List.contains() dans une boucle → Set. Gros volumes en mémoire → SOQL for loop.
// Avant : n × m comparaisons
for (Contact c : contacts) {
    for (Account a : accounts) {
        if (c.AccountId == a.Id) { c.Description = a.Industry; }
    }
}
// Après : une recherche par contact
Map<Id, Account> byId = new Map<Id, Account>(accounts);
for (Contact c : contacts) {
    Account a = byId.get(c.AccountId);
    if (a != null) { c.Description = a.Industry; }
}

Ordre d'exécution officiel (save order)

  1. Charge l'enregistrement d'origine, ou l'initialise pour un upsert.
  2. Charge les nouvelles valeurs. Validations système : depuis l'interface (règles de mise en page, champs requis, formats, longueurs) ; depuis Apex ou l'API, seulement les clés étrangères et les picklists restreintes.
  3. Flows before-save (mise à jour rapide des champs).
  4. Triggers before.
  5. Validations système à nouveau, puis règles de validation personnalisées.
  6. Duplicate rules : si une règle bloque, l'enregistrement s'arrête là.
  7. Sauvegarde en base, sans commit.
  8. Triggers after.
  9. Assignment rules.
  10. Auto-response rules.
  11. Workflow rules (legacy) : une mise à jour de champ relance une seule fois les triggers before update et after update.
  12. Escalation rules.
  13. Process Builder et flows lancés par des processus (legacy), sans ordre garanti.
  14. Flows after-save.
  15. Entitlement rules.
  16. Roll-up summary : le parent est recalculé et repasse par la sauvegarde, puis le grand-parent si besoin.
  17. Partage par critères.
  18. Commit de toutes les opérations DML.
  19. Après le commit : envoi des e-mails, exécution des jobs asynchrones en file (Queueable, future), chemins asynchrones des Flows.
