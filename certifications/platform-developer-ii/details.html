Multi-devises & localisation

Scénario type : l'org a l'euro comme devise d'entreprise, un commercial américain consulte des opportunités en EUR, GBP et USD. Il veut voir chaque montant dans sa devise et formaté à l'américaine, et un rapport doit totaliser les montants par étape.

// Montant converti dans la devise de l'utilisateur, puis formaté selon sa locale
List<Opportunity> opps = [
    SELECT Name, CurrencyIsoCode, FORMAT(convertCurrency(Amount))
    FROM Opportunity
    WHERE Amount > USD100000      // comparaison en tenant compte des devises
];

// Agrégat avec GROUP BY : résultat dans la devise de l'org, pas convertible
List<AggregateResult> totals = [
    SELECT StageName, SUM(Amount) total FROM Opportunity GROUP BY StageName
];

Avec Advanced Currency Management, la conversion des opportunités utilise le taux daté qui correspond à la date de l'enregistrement (CloseDate). Activer le multi-devises est irréversible, et une org qui référence CurrencyIsoCode dans son Apex ne peut plus le désactiver.

// Localisation en Apex
Datetime closedAt = opp.LastModifiedDate;   // stocké en GMT
String affichage = closedAt.format();       // fuseau + locale de l'utilisateur courant
String libelle = System.Label.Bienvenue;    // Custom Label traduit dans la langue de l'utilisateur

// Localisation en LWC
import LOCALE from '@salesforce/i18n/locale';
import CURRENCY from '@salesforce/i18n/currency';
import BIENVENUE from '@salesforce/label/c.Bienvenue';
Pourquoi c'est testéLes questions combinent souvent convertCurrency, FORMAT et GROUP BY pour vérifier que vous savez dans quelle devise arrive chaque valeur.

Partage programmatique (Apex managed sharing)

Scénario type : un objet personnalisé Projet__c en OWD Private ; le chef de projet, désigné dans un champ lookup, doit pouvoir modifier le projet, même si le propriétaire change. Aucune Sharing Rule ne peut exprimer « l'utilisateur du champ Chef_de_projet__c » : c'est un cas d'Apex managed sharing.

Projet__Share share = new Projet__Share(
    ParentId      = projet.Id,
    UserOrGroupId = projet.Chef_de_projet__c,
    AccessLevel   = 'Edit',
    RowCause      = Schema.Projet__Share.RowCause.Chef_de_projet__c  // Apex Sharing Reason
);
Database.SaveResult sr = Database.insert(share, false);
if (!sr.isSuccess()) {
    // ex. un accès égal ou inférieur à l'OWD : le partage est inutile et refusé
}
  • Sur AccountShare, les champs s'appellent AccountId et AccountAccessLevel, et il faut aussi préciser l'accès aux opportunités et aux cas.
  • Un partage Manual disparaît au changement de propriétaire ; un partage avec Apex Sharing Reason reste.
  • Après un changement d'OWD ou pour réparer des partages, la classe déclarée dans « Apex Sharing Recalculation » (un Database.Batchable) recrée les lignes.

Custom Metadata Types vs Custom Settings

Règle simple : configuration qui doit voyager avec le code (taux, mappings, interrupteurs de fonctionnalité) → Custom Metadata Type ; valeur qui dépend de l'utilisateur ou du profil et change à l'exécution → Custom Setting Hierarchy ; texte affiché et traduit → Custom Label.

// Custom Metadata : lu sans SOQL, déployé avec le code
Map<String, Tva__mdt> taux = Tva__mdt.getAll();
Decimal tauxFr = Tva__mdt.getInstance('FR').Taux__c;

// Custom Setting Hierarchy : la valeur la plus spécifique (utilisateur, sinon profil, sinon org)
Preferences__c prefs = Preferences__c.getInstance(UserInfo.getUserId());
prefs.Derniere_Vue__c = 'Kanban';
upsert prefs;   // crée la valeur propre à cet utilisateur
PiègeUn test qui lit un Custom Setting échoue sur une org vierge : ses valeurs ne sont pas visibles dans les tests et doivent y être créées. Les enregistrements de Custom Metadata, eux, sont visibles.
Process Automation, Logic, and Integration · 27 %

Automatisation, logique & intégration

Déclaratif ou code : qui s'exécute quand ?

Scénario : à la création d'un Case, un Flow before-save remplit la priorité, un trigger before normalise l'objet, une règle de validation contrôle le canal, un trigger after crée une tâche, une assignment rule choisit le propriétaire, puis un Flow after-save met à jour le Case. Cette dernière mise à jour relance une sauvegarde complète du Case, triggers compris, avant le commit.

  • Mise à jour de champs du même enregistrement : Flow before-save (rapide, sans DML) ou trigger before.
  • Création ou mise à jour d'autres enregistrements, appel de logique complexe ou de gros volumes : trigger after, ou Flow after-save s'il reste simple.
  • Callout ou traitement après le commit : chemin asynchrone du Flow, ou Queueable.
  • Workflow Rules et Process Builder ne doivent plus être utilisés : ils sont en fin de support depuis le 31/12/2025.
Pourquoi c'est testéLes scénarios mélangent Flow et triggers pour vérifier que vous savez ce qui s'exécute avant quoi, et ce qui peut relancer les triggers.

Triggers : bonnes pratiques

Un trigger fin, une classe handler qui porte le mode de partage (depuis Summer '26, le trigger lui-même s'exécute toujours en mode système), et une garde de récursion par enregistrement plutôt qu'un simple booléen.

public with sharing class OpportunityHandler {
    private static Set<Id> processed = new Set<Id>();

    public static void afterUpdate(Map<Id, Opportunity> newMap, Map<Id, Opportunity> oldMap) {
        List<Opportunity> changed = new List<Opportunity>();
        for (Opportunity o : newMap.values()) {
            if (processed.contains(o.Id)) continue;
            processed.add(o.Id);
            if (o.StageName != oldMap.get(o.Id).StageName) changed.add(o);
        }
        // logique bulkifiée sur changed
    }
}

Un booléen statique bloque aussi les lots suivants de la même transaction (au-delà de 200 enregistrements, un trigger est appelé par lots de 200) : le Set<Id> évite ce piège.

Apex asynchrone : bénéfices et choix

Grille de décision : traitement ponctuel simple → Future ; sObjects en paramètre, chaînage ou suivi → Queueable ; dizaines de milliers à millions d'enregistrements → Batch Apex, ou Apex Cursors dans une chaîne de Queueables ; tâche récurrente → Scheduled Apex, qui lance souvent un batch.

// Apex Cursors (GA en API 66.0) : parcourir un gros volume en chaîne de Queueables
public class ReindexJob implements Queueable {
    private Database.Cursor cursor;
    private Integer position;

    public ReindexJob(Database.Cursor cursor, Integer position) {
        this.cursor = cursor;
        this.position = position;
    }
    public void execute(QueueableContext ctx) {
        List<Account> chunk = cursor.fetch(position, 2000);
        // traitement du lot
        position += chunk.size();
        if (position < cursor.getNumRecords()) {
            System.enqueueJob(new ReindexJob(cursor, position));
        }
    }
}
Database.Cursor c = Database.getCursor('SELECT Id FROM Account WHERE Needs_Reindex__c = true');
System.enqueueJob(new ReindexJob(c, 0));

Chaque fetch() compte comme une requête SOQL et ses lignes dans la limite de lignes ; la classe Limits suit aussi la consommation des curseurs.

// Transaction Finalizer : réagir à l'échec d'un Queueable
public class RetryFinalizer implements Finalizer {
    public void execute(FinalizerContext ctx) {
        if (ctx.getResult() == ParentJobResult.UNHANDLED_EXCEPTION) {
            // journaliser ctx.getException(), relancer le job si besoin
        }
    }
}
// Dans execute() du Queueable :
System.attachFinalizer(new RetryFinalizer());

Apex dynamique

Le choix de la classe à exécuter vient d'une configuration plutôt que du code : c'est le cas d'usage typique de Type.forName() avec une interface.

public interface DiscountStrategy { Decimal apply(Decimal amount); }

String className = Discount_Config__mdt.getInstance('Default').Strategy_Class__c;
DiscountStrategy strategy = (DiscountStrategy) Type.forName(className).newInstance();
Decimal net = strategy.apply(order.Amount__c);

Pour du SOQL dynamique, Database.queryWithBinds() évite la concaténation (et l'injection SOQL) et précise le mode d'accès. String.escapeSingleQuotes() reste une solution de repli quand on doit concaténer.

// Abonnement Apex : trigger after insert uniquement
trigger OrderShippedTrigger on Order_Shipped__e (after insert) {
    for (Order_Shipped__e evt : Trigger.new) {
        // traitement ; en cas d'erreur temporaire :
        // throw new EventBus.RetryableException('Service indisponible');

  • Le trigger s'exécute par défaut avec l'utilisateur Automated Process : les champs « créé par » et les traces de debug en dépendent. PlatformEventSubscriberConfig change cet utilisateur et la taille de lot.
  • Côté externe, la Pub/Sub API (gRPC, HTTP/2, messages binaires Avro) publie et s'abonne aux Platform Events high-volume et à CDC. Elle ne gère pas les événements legacy (standard-volume, PushTopic, generic).
  • CDC plutôt que Platform Event : quand le besoin est « notifier tout changement d'enregistrement » sans code de publication.

Gestion des erreurs & intégrité transactionnelle

public class InsufficientStockException extends Exception {}

Savepoint sp = Database.setSavepoint();
try {
    insert order;
    if (stock < quantity) throw new InsufficientStockException('Stock insuffisant');
    insert lines;
} catch (Exception e) {
    Database.rollback(sp);   // annule la commande et les lignes
    throw new AuraHandledException(e.getMessage());
}
  • Pour un import tolérant aux erreurs : Database.insert(records, false), puis parcourir les SaveResult.
  • Un rollback ne rend pas les DML consommés dans les limites, et les enregistrements gardent leur Id en mémoire : les réinsérer tels quels échoue.
  • Aucune construction ne peut intercepter une LimitException : la prévention passe par la bulkification et la classe Limits.

Trouver pourquoi le code ne fait pas ce qui est prévu

  • Aucun log pour un trigger de Platform Event ? Il s'exécute comme Automated Process : le trace flag doit viser cette entité, pas votre utilisateur.
  • Un test passe en sandbox et échoue ailleurs : chercher une dépendance aux données de l'org (SeeAllData, Custom Settings non créés, Id codés en dur).
  • Un comportement change selon l'utilisateur : vérifier le mode de partage de la classe, le mode d'accès des requêtes (user mode par défaut en API 67.0) et les permissions.
  • Le Log Inspector montre où part le temps (Timeline, Performance Tree) ; l'Apex Replay Debugger permet de parcourir le log pas à pas dans VS Code.
