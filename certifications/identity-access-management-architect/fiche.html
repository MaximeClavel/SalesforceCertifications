Identity Management Concepts · 17 %

Concepts de gestion des identités

Qui authentifie, qui fait confiance à qui, et avec quel standard.

0/4
Objectifs de la section
  • Décrire le rôle du fournisseur d'identité (IdP) et du fournisseur de service (SP) dans une solution de contrôle d'accès.
  • Décrire comment s'établit la confiance entre deux systèmes.
  • Décrire les composants et les risques de l'authentification déléguée.
  • Choisir le standard adapté (SAML, OAuth 2.0, OpenID Connect, SCIM) et décrire le cycle de vie des identités.

IdP, SP et confiance

  • Fournisseur d'identité (IdP) : authentifie l'utilisateur et émet une assertion ou un jeton. Fournisseur de service (SP) : fait confiance à cette assertion et donne l'accès.
  • Salesforce peut être SP (les employés se connectent avec Okta, Entra ID, Ping) ou IdP (des applications tierces font confiance à Salesforce).
  • Confiance SAML : échange de métadonnées. Le SP connaît l'Issuer et le certificat de signature de l'IdP ; l'IdP connaît l'Entity ID et l'URL ACS (Assertion Consumer Service) du SP.
  • SP-initiated : l'utilisateur arrive sur le SP (lien profond, My Domain), est redirigé vers l'IdP, puis revient sur la page demandée (RelayState). IdP-initiated : l'utilisateur part du portail de l'IdP.
PiègeLes rôles s'inversent selon le sens : quand Salesforce consomme l'assertion d'Okta, Okta est l'IdP et Salesforce le SP.

Authentification déléguée

  • À chaque connexion, Salesforce envoie l'identifiant et le mot de passe (ou un jeton) à un service web SOAP de l'entreprise, qui répond vrai ou faux.
  • Activée sur demande à Salesforce ; s'applique aux utilisateurs dont le profil ou un permission set porte « Is Single Sign-On Enabled ».
  • Risques : la connexion dépend de la disponibilité du service ; le mot de passe transite par Salesforce. La fédération SAML ou OpenID Connect est préférée : Salesforce ne voit jamais le mot de passe.

Cycle de vie des identités

  • Arrivée, mobilité, départ (joiner, mover, leaver) : la source de vérité est souvent le SIRH, propagé à l'annuaire puis aux applications.
  • Provisionnement : manuel, Just-in-Time à la connexion (création ou mise à jour seulement), ou par API (SCIM, outil d'IAM) qui gère aussi la désactivation.
  • Départ : on ne supprime pas un utilisateur Salesforce. On le gèle (Freeze, effet immédiat, même quand la désactivation est bloquée par des champs de hiérarchie), puis on le désactive et on révoque ses jetons OAuth.
PiègeCouper l'accès à l'IdP ne suffit pas : les sessions ouvertes et les jetons OAuth restent valides tant qu'ils ne sont pas révoqués.

Identité tierce dans Salesforce

Salesforce fournisseur de service : SSO SAML, fournisseurs d'authentification, provisionnement à la connexion.

0/4
Objectifs de la section
  • Configurer le SSO SAML avec un IdP tiers, y compris plusieurs IdP.
  • Configurer les fournisseurs d'authentification (OpenID Connect, réseaux sociaux, autre org Salesforce) et leur registration handler.
  • Choisir et mettre en œuvre le provisionnement Just-in-Time.
  • Diagnostiquer les échecs de connexion fédérée.

SSO SAML vers Salesforce

  • Toutes les orgs ont un My Domain : c'est l'URL de connexion propre à l'org, utilisée par le SSO.
  • Single Sign-On Settings : Issuer, certificat de l'IdP, URL de connexion de l'IdP, SAML Identity Type (nom d'utilisateur, Federation ID ou ID utilisateur Salesforce) et emplacement de l'identité (Subject ou attribut).
  • Quand les identifiants diffèrent entre l'annuaire et Salesforce, on stocke l'identifiant de l'annuaire dans le Federation ID de l'utilisateur.
  • Bouton de l'IdP sur la page de connexion : My Domain → Authentication Configuration → Authentication Service. On peut y masquer le formulaire classique et interdire la connexion par login.salesforce.com.
  • Plusieurs IdP (filiales, acquisitions) : une configuration SAML par IdP, toutes proposées sur la page de connexion, ou un Login Discovery qui choisit l'IdP selon l'identifiant saisi (Auth.MyDomainLoginDiscoveryHandler).
  • Application mobile Salesforce : elle doit utiliser l'URL My Domain (réglée par l'utilisateur ou déployée par MDM) pour proposer l'IdP.

Provisionnement Just-in-Time

  • JIT SAML : à la connexion, Salesforce crée ou met à jour l'utilisateur à partir des attributs de l'assertion. Le JIT standard accepte des attributs de l'utilisateur (dont le profil et le rôle) ; pour une logique sur mesure (permission sets, règles de mapping), on écrit un handler qui implémente Auth.SamlJitHandler (createUser, updateUser).
  • Fournisseurs d'authentification : le Auth.RegistrationHandler est appelé avec les données de l'IdP. createUser s'exécute à la première connexion (pas encore de lien), updateUser aux connexions suivantes.
  • Le JIT ne désactive personne : il ne s'exécute qu'à la connexion. Le départ d'un employé passe par un autre mécanisme (SCIM, outil d'IAM, procédure).
global class CorpRegistrationHandler implements Auth.RegistrationHandler {
    // Première connexion par ce fournisseur : créer (ou retrouver) l'utilisateur
    global User createUser(Id portalId, Auth.UserData data) { … }
    // Connexions suivantes : mettre à jour l'utilisateur déjà lié
    global void updateUser(Id userId, Id portalId, Auth.UserData data) { … }
}

Fournisseurs d'authentification

  • Types : OpenID Connect (n'importe quel IdP compatible), Google, Facebook, Apple, Microsoft, LinkedIn, GitHub, Salesforce (une autre org)…
  • Configuration OpenID Connect : consumer key et secret émis par l'IdP, URL d'autorisation, de jeton et UserInfo, scopes, registration handler. Le fournisseur est ensuite ajouté à la page de connexion.
  • SSO entre deux orgs Salesforce : l'org cible définit un fournisseur de type Salesforce qui pointe vers l'org source (ou l'org source est IdP SAML de l'autre). Salesforce to Salesforce partage des données, pas des identités.

MFA fédérée et diagnostic

  • Avec le SSO, l'exigence de MFA de Salesforce peut être satisfaite par la MFA de l'IdP : l'utilisateur ne la refait pas dans Salesforce.
  • Avantages de la fédération sur l'authentification déléguée : Salesforce ne reçoit jamais le mot de passe, et les politiques (MFA, verrouillage, départ) sont appliquées au même endroit.
  • Diagnostic : SAML Assertion Validator (dans les paramètres SSO) et Login History. Causes fréquentes : horloge décalée (assertion expirée), certificat ou Issuer différents, Federation ID absent.
PiègeLes debug logs n'aident pas à diagnostiquer une assertion SAML refusée.

Salesforce fournisseur d'identité

Connected apps, flux OAuth et OpenID Connect, provisionnement vers les applications.

0/4
Objectifs de la section
  • Configurer Salesforce comme IdP SAML pour des applications tierces.
  • Choisir le flux OAuth adapté au type d'application.
  • Configurer les politiques des connected apps (utilisateurs autorisés, scopes, jetons).
  • Provisionner les utilisateurs vers les applications connectées.

Salesforce IdP SAML

  • Activer Identity Provider dans Setup, avec un certificat de signature.
  • Créer une connected app (ou une external client app) avec SAML : Entity ID et URL ACS de l'application, type de sujet, format de Name ID, URL de connexion initiée par l'IdP.
  • Accès : profils et permission sets de l'application ; l'application apparaît dans l'App Launcher.
  • User Provisioning for Connected Apps : créer, mettre à jour et désactiver les comptes dans l'application tierce quand on attribue ou retire l'accès.
  • Single Logout : à configurer dans l'application et la connected app pour fermer les sessions des applications à la déconnexion.

Politiques des connected apps

  • Permitted Users : « All users may self-authorize » (chaque utilisateur accepte l'accès) ou « Admin approved users are pre-authorized » (seuls les profils ou permission sets attribués à l'application, sans écran d'autorisation).
  • Refresh Token Policy : valide jusqu'à révocation, expiration immédiate, expiration après une durée, ou expiration s'il n'est pas utilisé pendant une durée.
  • Scopes au plus juste : api, refresh_token (offline_access), openid, id, web ; full donne tout.
  • IP Relaxation, durée de session, High Assurance session required pour exiger une session de niveau élevé.
  • Salesforce pousse désormais les External Client Apps, qui remplacent progressivement les connected apps, avec des réglages plus sûrs par défaut.

Salesforce fournisseur OpenID Connect

  • Scope openid : Salesforce renvoie un ID token (JWT signé) en plus du jeton d'accès.
  • L'application valide la signature avec les clés publiques de /id/keys, découvertes par /.well-known/openid-configuration.
  • Endpoint UserInfo (et identity URL) : informations sur l'utilisateur. Révocation : /services/oauth2/revoke. Introspection : /services/oauth2/introspect.
Access Management Best Practices · 15 %

Bonnes pratiques d'accès

MFA, sessions, restrictions réseau, autorisations et audit.

0/4
Objectifs de la section
  • Décrire les risques couverts par la MFA et les niveaux de sécurité de session.
  • Recommander les contrôles de connexion et de session adaptés.
  • Attribuer les droits (profils, rôles, permission sets) dans un scénario de SSO.
  • Auditer l'activité après connexion et les applications connectées.

MFA

  • Exigée pour toutes les connexions à l'interface : MFA de Salesforce pour les connexions directes, MFA de l'IdP pour les connexions SSO.
  • Méthodes acceptées : Salesforce Authenticator, application TOTP, clé de sécurité (WebAuthn, U2F), authentificateur intégré (Touch ID, Windows Hello). Ni SMS, ni e-mail.
  • Comptes exemptés (tests d'interface automatisés) : permission « Waive Multi-Factor Authentication for Exempt Users ». Les connexions par API ne sont pas concernées.
  • Lightning Login : connexion sans mot de passe pour les utilisateurs internes, avec Salesforce Authenticator.

Connexion et sessions

  • Login IP Ranges (profil) : connexion refusée hors des plages. Trusted IP Ranges (Network Access) : pas de vérification d'identité depuis ces plages, mais connexion possible ailleurs.
  • Login Hours (profil) : connexion seulement pendant les heures définies.
  • Niveaux de session : Standard et High Assurance. Une connected app, un rapport ou une action peut exiger High Assurance : l'utilisateur doit alors valider la MFA.
  • Session Settings : verrouiller la session à l'adresse IP et au domaine d'origine, durée d'inactivité, attribut HttpOnly.
  • Login Flows : un flow après l'authentification (accepter des conditions, vérification supplémentaire), attribué par profil.
  • Transaction Security Policies (Real-Time Event Monitoring) : bloquer ou alerter en temps réel, par exemple sur un export de rapport volumineux.

Autorisations

  • Moindre privilège : profil minimal, droits par permission sets et permission set groups.
  • En SSO, les droits peuvent suivre les groupes de l'annuaire : le handler JIT ou l'outil de provisionnement attribue profil, rôle et permission sets.
  • Applications connectées : accès par profil ou permission set, scopes réduits.

Audit et réaction

  • Login History (connexions, méthode, statut), Identity Verification History, Setup Audit Trail (changements de configuration, 180 jours), Event Monitoring (LoginEvent, API, rapports), Identity Provider Event Log.
  • Application compromise : sur la page Connected Apps OAuth Usage, révoquer ses jetons et la bloquer.
Salesforce Identity · 12 %

Salesforce Identity

Licences, App Launcher, endpoints et vérification d'identité.

0/3
Objectifs de la section
  • Choisir les licences Identity selon le public (employés, clients).
  • Décrire les fonctionnalités de Salesforce Identity : App Launcher, SSO, provisionnement, déconnexion unique.
  • Utiliser les endpoints d'identité et les méthodes de vérification.

Licences

  • Identity (Identity Only) : employés qui utilisent Salesforce comme IdP et l'App Launcher, sans fonctions CRM.
  • External Identity : clients et consommateurs à grande échelle (B2C), avec un site Experience Cloud pour la connexion et l'inscription.
  • Licences Experience Cloud (Customer Community, Customer Community Plus, Partner Community) : quand les utilisateurs externes travaillent sur des données CRM.

Fonctionnalités et endpoints

  • App Launcher, Salesforce IdP SAML et OpenID Connect, provisionnement vers les applications, Single Logout.
  • SCIM 2.0 : /services/scim/v2/Users pour qu'un outil d'IAM crée, mette à jour et désactive les utilisateurs.
  • Jetons : /services/oauth2/token (obtenir, renouveler), /revoke, /introspect ; /services/oauth2/userinfo et l'identity URL pour les informations de l'utilisateur.
  • Headless Identity : API d'inscription, de connexion, de connexion sans mot de passe et de mot de passe oublié, pour une application qui garde sa propre interface.

My Domain et vérification

  • My Domain est obligatoire et actif dans toutes les orgs ; changer son nom change les URL de connexion et impose de mettre à jour les configurations SSO.
  • Vérification d'identité : méthodes MFA, Lightning Login ; pour les utilisateurs externes, codes par e-mail ou SMS (connexion sans mot de passe).

PiègeLes utilisateurs à grand volume (Customer Community) ne peuvent pas figurer dans des règles de partage : on passe par les sharing sets.

Inscription et connexion

  • Réglages dans Experience Workspaces → Administration → Login & Registration.
  • Auto-inscription : compte par défaut pour les contacts (ou comptes personnels), page d'inscription configurable avec champs supplémentaires et vérification par e-mail ou SMS, handler Auth.ConfigurableSelfRegHandler pour une logique sur mesure.
  • Connexion sans mot de passe : code à usage unique par e-mail ou SMS.
  • Réseaux sociaux : fournisseurs d'authentification et registration handler, ajoutés à la page de connexion du site.
  • Partenaires avec leur propre IdP : une configuration SAML par partenaire, activée pour le site, avec JIT pour créer les utilisateurs partenaires.
  • Login Discovery du site : l'utilisateur saisit son e-mail ou son téléphone, un handler le dirige vers son IdP ou vers un code (Auth.LoginDiscoveryHandler).

Accès invité

  • Profil invité : seulement les droits d'objet et de champ nécessaires aux pages publiques ; jamais View All ni Modify All.
  • Partage vers les invités par des règles de partage pour invités, en lecture seule.
  • Les enregistrements créés par un invité sont attribués à un propriétaire interne par défaut.

Applications externes

  • Application native qui veut son propre écran de connexion : Headless Identity (Authorization Code and Credentials flow), sans page web Salesforce.
  • Application qui accepte une page web : flux web server avec PKCE vers le site Experience Cloud.
  • Le flux username-password n'est pas une solution pour les clients.
